# Rust: практический справочник по оптимизации производительности

> **Единый Markdown-файл.** Редакция: 2026-11-09; сверено с официальными данными Rust по состоянию на 2026-11-09. Язык: русский. Ориентир: стабильный Rust, прежде всего Linux/x86-64; stable Rust 1.99.1, оговорки по MSRV указаны отдельно; большинство приёмов переносимы.  
> **Цель:** уменьшить время выполнения, задержки, количество аллокаций, расход памяти, размер бинарника и/или время сборки **без незаявленного изменения поведения**.  
> **Важное ограничение:** исчерпывающего перечня «вообще всех» оптимизаций не существует — они зависят от задачи, ОС, процессора, версии компилятора и входных данных. Здесь собрана широкая практическая карта техник, а не обещание автоматического ускорения. Примеры иллюстративны; в среде редактирования не установлен `rustc`, поэтому **ни один новый Rust-пример не выдаётся за скомпилированный**. Отдельный учебный Cargo-проект приложен для локальной проверки; результаты ускорения не выдуманы.

## 1. Как пользоваться справочником

**Не превращайте список в набор обязательных правил.** Здесь перечислены *кандидаты* на оптимизацию. Без измерения можно обоснованно утверждать, например, что переход от поиска `O(n²)` к `O(n log n)` улучшает асимптотику или что повторное использование `Vec` уменьшает число возможных аллокаций. Но это **не равно** утверждению «весь проект станет быстрее на X%». Для конкретных входов накладные расходы способны перевернуть результат.

У каждой техники в каталоге есть короткий формат: **что сделать → где помогает → когда вредит / что проверять**. Условные маркеры:

- **[П]** — обычно высокий приоритет, проверить в начале;
- **[М]** — зависит от профиля, входных данных и размера задачи;
- **[Э]** — экспертная техника с рисками совместимости, точности, безопасности либо сопровождаемости;
- **[В]** — меняет внешний контракт или может изменить порядок, округление, паники и т. п.

**Оптимизация ≠ «сложнее и ближе к железу».** Самые полезные изменения часто заключаются в сокращении количества работы, удалении аллокаций, подходящем контейнере и устранении ненужных копий. По мере роста сложности кода нужна всё более веская демонстрация выигрыша. Общие принципы: [Rust Performance Book — General Tips](https://nnethercote.github.io/perf-book/general-tips.html).

### Суперкороткий маршрут: что проверять в первую очередь

1. `cargo build --release` и замер **реальной** нагрузки.
2. Убрать работу из горячего пути: лишние сортировки, повторные поиски, повторный парсинг.
3. В горячих циклах убрать ненужные `.clone()`, `.to_owned()`, `format!` и временные `Vec`.
4. Если объём известен — проверить `with_capacity` и повторное использование буфера.
5. Проверить структуру данных: `Vec` / `VecDeque` / `HashMap` / `BTreeMap` / bitset.
6. Заменить повторный `contains_key`+`insert` на `entry`, если это та же логика.
7. Для I/O проверить `BufReader`, `BufWriter`, `stdout().lock()` и размер batch.
8. Для массивов проверить локальность памяти, порядок прохода, `zip`/`chunks_exact` **с правильными длинами**.
9. Для потоков измерить contention и стоимость задач, ограничить мелкую параллельность.
10. Только после этого сравнивать LTO, `codegen-units`, PGO, SIMD и `unsafe`.

## 2. Порядок действий для реального проекта

1. **Определите критерий.** Throughput (операций/с), latency p50/p95/p99, время единичной задачи, пиковая память, бинарный размер или сборка — это разные цели.
2. **Фиксируйте корректность.** Напишите тесты, проверяющие выход, порядок элементов, ошибки, Unicode, переполнение, пустые массивы и крайние случаи.
3. **Замерьте исходную версию.** Только оптимизированная сборка для runtime; используйте реальную нагрузку и несколько размеров данных.
4. **Найдите узкое место.** `perf`, flamegraph, DHAT/heaptrack, `perf stat`, профилирование I/O. Измеряйте, а не угадывайте по коду.
5. **Сначала алгоритм и архитектура**, затем память/контейнеры, затем циклы/CPU; менять флаги компиляции тоже полезно, но не вместо первых шагов.
6. **Одно изменение за раз.** Соберите, проверьте эквивалентность, повторите тесты и замеры; сохраняйте diff, машину и компилятор.
7. **Оставляйте правку, только если выигрыш стабилен** в нужных сценариях и оправдывает регрессии, увеличение памяти, размер кода и поддержку.

### Минимальный воспроизводимый запуск

```bash
rustc -Vv
cargo test
cargo clippy --all-targets --all-features -- -D warnings
cargo build --release

# Linux: системные счётчики и семплирование горячих функций
perf stat -r 7 -- ./target/release/my_program input.dat
# -g по умолчанию опирается на frame pointers; в release-сборке Rust их нет,
# поэтому стеки будут обрезаны. Либо соберите с frame pointers (см. §29.1),
# либо возьмите --call-graph dwarf (нужен debuginfo):
perf record -g --call-graph dwarf -- ./target/release/my_program input.dat
perf report
```

`my_program` и `input.dat` здесь замените на ваши имена. `perf` может потребовать настройки прав доступа. `-D warnings` — строгий режим, не каждая рекомендация Clippy означает ускорение.

## 3. Сборка, оптимизатор LLVM и параметры Cargo

**Проверенный факт:** Cargo `release` уже имеет `opt-level = 3` по умолчанию. Повторное указание `opt-level = 3` само по себе не ускоряет проект. Разные режимы LTO и `codegen-units` имеют компромиссы со временем сборки; `opt-level = 2` иногда работает лучше `3`. Источник: [Cargo Profiles](https://doc.rust-lang.org/cargo/reference/profiles.html).

| ID | Приём | Когда использовать | Риск / нюанс |
|---|---|---|---|
| B01 [П] | Собирать исполняемый код через `cargo build --release` | Любой замер производительности | `cargo test` без профиля по умолчанию использует менее оптимизированный код |
| B02 [М] | Сравнить `opt-level = 2` и `3` | CPU-bound код, размеры и латентность | `3` может проигрывать из-за размера/кэша инструкций |
| B03 [М] | `lto = "thin"` | Кросс-крейт инлайнинг, небольшие/средние сервисы | Увеличивает время линковки |
| B04 [М] | `lto = "fat"` | Максимизация runtime в завершённой сборке | Очень дорогая линковка, не гарантирует выигрыш |
| B05 [М] | `codegen-units = 1` | Более глубокая оптимизация и возможность инлайнинга | Меньше параллелизма LLVM; сборка дольше |
| B06 [М][В] | `panic = "abort"` | Размер бинарника и стоимость раскрутки | Паника немедленно завершает процесс; не вызывается обычная раскрутка стека |
| B07 [М] | `-C target-cpu=native` | Запуск **на том же CPU**, что использовался для сборки | Бинарник может не работать на старом CPU |
| B08 [Э][В] | `-C target-feature=+avx2` и другие флаги | Заранее известная аппаратная платформа | Нарушение требований к CPU может сделать программу неработоспособной; риск неверного кода при ошибочной конфигурации |
| B09 [М] | PGO: `-C profile-generate` → реальные запуски → `-C profile-use` | Стабильные типовые нагрузки, важны ветвления/раскладка | Плохой профиль ухудшит работу на других входах |
| B10 [М] | LLVM BOLT / `cargo-pgo` (внешние инструменты) | Крупные производственные бинарники | Инструментарий платформозависим; требует отдельных замеров |
| B11 [М] | Альтернативный аллокатор (`mimalloc`, `jemalloc` и др.) | Если профиль показывает высокую стоимость malloc/free | Внешняя зависимость; потребление памяти и задержки могут измениться |
| B12 [М] | Быстрый linker (`mold`, `lld`) | Долгая линковка в CI | Преимущественно ускорение **сборки**, а не runtime |
| B13 [М] | `strip = "symbols"` или `strip = "debuginfo"` | Уменьшение размера релизного файла | Меньше информации для диагностики; runtime-эффект необязателен |
| B14 [П] | `debug = "line-tables-only"` при профилировании | Чтобы сохранить привязку адресов к строкам | Дополнительный размер отладочных секций |
| B15 [М] | `opt-level = "s"` / `"z"` | Фокус на размере бинарника | Не гарантирует минимальный размер, часто ухудшает скорость; `z` может отключать векторизацию |
| B16 [М] | Разные Cargo profiles для разработки и финального релиза | Быстрые edit-build-test циклы + хороший production | Результаты в `dev` нельзя переносить на `release` |
| B17 [М] | Отключить ненужные features зависимостей | Бинарный размер, запуск, время сборки | Иногда уменьшает функциональность; необходимы регрессионные тесты |
| B18 [М] | При большом проекте использовать `cargo check` вместо `cargo build` на части итераций | Ускорение обратной связи компилятора | `check` не порождает исполнительный бинарник; не заменяет runtime-тесты |
| B19 [М] | `incremental = true` для разработки | Повторные сборки | Дополнительные файлы и иногда ухудшение качества оптимизации/скорости сборки |
| B20 [Э] | Профилировать время и память самой сборки; ограничить макросы/мономорфизации | Большие crates | Компромисс runtime/размер кода/время компиляции |

### Начальная конфигурация для эксперимента

```toml
# Cargo.toml
[profile.release]
opt-level = 3
lto = "thin"
codegen-units = 1
panic = "abort"
```

Это **отправная точка для сравнения**, а не универсальная рекомендация и не эквивалент стандартного релизного профиля. Не включайте `panic = "abort"`, если требуется перехват паник или корректная раскрутка; не включайте LTO, пока не измерили стоимость сборки. Для максимально переносимого бинарника не используйте `target-cpu=native` без контроля архитектуры целевых серверов.

```bash
RUSTFLAGS="-C target-cpu=native" cargo build --release
# Для восстановления нормальной переносимости:
cargo clean
cargo build --release
```

**PGO:** официальный пошаговый процесс см. в [rustc PGO](https://doc.rust-lang.org/rustc/profile-guided-optimization.html). Не переносите архив профиля от чужой программы/версии бинарника.

## 4. Профилирование и корректные бенчмарки

| ID | Инструмент / техника | Что ищет | На что смотреть |
|---|---|---|---|
| M01 [П] | `perf record`, `perf report`, flamegraph | Hot paths, стеки вызовов | Куда реально уходит CPU-время |
| M02 [П] | `perf stat` (`cycles`, `instructions`, `cache-misses`, `branch-misses`) | Счётчики CPU | Больше инструкций не всегда значит медленнее |
| M03 [М] | DHAT, heaptrack, Valgrind Massif | Аллокации и пиковое потребление памяти | Частота/размер/время жизни объектов |
| M04 [М] | Cachegrind/Callgrind | Инструкции, кэш и ветвления | Модель кэша условна; подтверждайте на реальном железе |
| M05 [М] | `cargo flamegraph`, `samply` | Удобный профиль функций | Сэмплирование и профилировочные символы |
| M06 [М] | Criterion.rs (внешний crate) | Микробенчмарки и распределение времен | Нельзя делать вывод по одному числу |
| M07 [М] | `hyperfine` (внешняя утилита) | Время запуска готовой программы | Включает запуск, файловый кэш, shell-overhead |
| M08 [П] | `std::hint::black_box` | Снизить риск устранения замеряемой работы оптимизатором | Не является абсолютной гарантией; не заменяет проверку результата |
| M09 [П] | Прогрев и много повторений | Устойчивость результатов | Учитывать turbo, частоты, планировщик, страницы памяти |
| M10 [П] | Несколько размеров данных и распределений | Переломы при переходе L1/L2/L3/DRAM | Малые `n` могут иметь обратный результат |
| M11 [М] | Перемежаемый порядок A–B–B–A (ABBA) | Снизить систематический дрейф | Замеры должны быть независимыми блоками |
| M12 [М] | CPU pinning (`taskset`), фиксированная нагрузка | Шум измерений | Само закрепление может менять поведение работы |

| M14 [М] | `cargo bloat`, `llvm-size`, `size` | Раздувание кода/бинарника | Distinguish debug symbols vs executable code |
| M15 [М] | `cargo llvm-lines` | Большие объёмы LLVM IR/мономорфизации | Для времени компиляции и размера кода |
| M16 [П] | Профиль на реальных входных данных | Несовпадение синтетических и реальных нагрузок | Избегайте «оптимизации бенчмарка» |
| M17 [П] | Контроль эквивалентности до бенчмарков | Семантические регрессии | Ошибки и краевые случаи важнее миллисекунд |
| M18 [М] | Мониторинг p95/p99, RSS, alloc/s, CPU% | Server / latency и память | Среднее время не показывает хвосты |

**Мини-бенчмарк только на `std`:**

```rust
use std::hint::black_box;
use std::time::Instant;

fn work(values: &[u64]) -> u64 {
    values.iter().fold(0_u64, |sum, &value| sum.wrapping_add(value))
}

fn main() {
    let values = vec![7_u64; 100_000];
    for _ in 0..10 {
        black_box(work(black_box(&values)));
    }

    let repetitions = 200;
    let start = Instant::now();
    for _ in 0..repetitions {
        black_box(work(black_box(&values)));
    }
    let ns_per_call = start.elapsed().as_nanos() as f64 / repetitions as f64;
    println!("{ns_per_call:.1} ns/call");
}
```

Этот пример **не выдаёт статистически достоверный результат**: для серьёзного сравнения повторите независимо обе версии, чередуя порядок, и сохраняйте сырые измерения. Для коротких функций делайте много операций в одном блоке; не меряйте только `Instant::now()` вокруг одиночной инструкции. `wrapping_add` в примере задаёт явную арифметику по модулю 2^64.

## 5. Алгоритмы и количество выполняемой работы

| ID | Приём | Помогает | Когда не помогает / риск |
|---|---|---|---|
| A01 [П] | Заменить алгоритм с `O(n²)` на `O(n log n)` / `O(n)` | Рост `n`, повторный поиск | На очень малых `n` константы могут перевесить |
| A02 [П] | Избавиться от повторного полного прохода по коллекции | Подсчёты, поиск, агрегирование | Если необходима повторная проверка после мутации |
| A03 [П] | Перенести инвариантные вычисления из цикла | Константные преобразования, длины, коэффициенты | Компилятор уже мог это сделать |
| A04 [П] | Вычислять только по требованию (lazy/on-demand) | Редкие ветви | Кеш/ленивость может увеличить задержку первого запроса |

| A08 [М] | Sliding window вместо пересчёта окна | Движущиеся агрегаты | Нужна осторожность при переполнении и уходящих элементах |
| A09 [М] | Двухуказательный проход по отсортированным последовательностям | Пересечение, слияние, фильтр | Нужен контракт сортировки |

| A15 [М] | Избегать работы над уже известным/отфильтрованным | Отбрасывание пакетов/событий | Проверки должны быть семантически корректными |
| A16 [М] | Batch/packet processing | Уменьшение вызовов, lock/syscall overhead | Память, latency до наполнения пакета |
| A17 [М] | Уменьшить число проходов (fusion) | Большие объёмы и memory bandwidth | Fusion иногда мешает SIMD или параллельности |

**Приоритет:** изменение алгоритмической сложности почти всегда стоит рассмотреть раньше ручного `unsafe`, AVX или принудительного inlining. Но не утверждайте выигрыш без измерения целевого workload.

## 6. Аллокации и владение памятью

Основная идея: не все аллокации плохи; оптимизируйте **горячие** аллокации. `Vec::new()` для пустого вектора не выделяет память. `Vec::with_capacity(n)` резервирует вместимость, но оставляет `len() == 0`. `SmallVec` не гарантирует ускорения — дополнительная логика и больший размер объекта иногда проигрывают обычному `Vec`. См. [Performance Book — Heap Allocations](https://nnethercote.github.io/perf-book/heap-allocations.html), [std::Vec](https://doc.rust-lang.org/std/vec/struct.Vec.html).

| ID | Приём | Когда полезен | Риски и оговорки |
|---|---|---|---|
| H01 [П] | `Vec::with_capacity(estimated_len)` | Число элементов заранее известно/оценивается | Завышение вместимости увеличивает RSS |
| H02 [М] | `Vec::reserve` / `reserve_exact` | Порциями увеличивать контейнер без частых realloc | `reserve_exact` не всегда экономит и может чаще перевыделять |
| H03 [П] | `vec.clear()` вместо создания нового в цикле | Повторяемые партии обработки | `clear` вызывает `Drop` элементов и сохраняет память |
| H04 [П] | `String::with_capacity` / `clear` | Сборка множества строк | Не превращать один короткий запрос в постоянно большой буфер |
| H05 [П] | Передать `&mut Vec<T>` вместо возврата нового временного вектора | Горячие функции-производители | Меняет API и контракт очистки/добавления |
| H06 [П] | `&str` вместо `String` для чтения текста | Чтение без владения | Ссылки не могут пережить исходный буфер |
| H07 [П] | `&[T]` вместо копирования `Vec<T>` | Аналитика/парсинг | Нужно обеспечить время жизни среза |
| H08 [П] | Убирать лишние `.clone()`, `.to_owned()`, `.to_string()` | В горячих местах создаются копии | Иногда копии нужны, чтобы снять блокировки/удержание ссылок |
| H09 [М] | `clone_from(&source)` для уже выделенного назначения | Много повторных перезаписей | Не всегда поддерживает существенное повторное использование |
| H10 [М] | `Cow<'a, str>` / `Cow<'a, [T]>` | Чаще borrowed, иногда owned | `to_mut()` может неожиданно копировать |
| H11 [М] | `Box<[T]>` вместо неизменяемого `Vec<T>` | Больше не нужна capacity, нужен только slice | Конвертация может перераспределить память; нет `push` |
| H12 [М] | `SmallVec<[T; N]>` — внешний crate | Очень много коротких векторов | Inline-объект больше; ветка heap/inline; дорогой Move |
| H13 [М] | `ArrayVec<T, N>` — внешний crate | Есть строгая верхняя граница размера | Переполнение вместимости требует обработки; заранее фиксированный размер |
| H14 [М] | Небольшой массив `[T; N]` + счётчик длины | Малые фиксированные буферы без зависимостей | Ручная логика и инициализация; хранить только корректные элементы |
| H15 [М] | Arena/bump allocation — внешние crates или свой дизайн | Множество короткоживущих объектов одного этапа | Деструкторы, память до конца арены, ссылки между эпохами |
| H16 [М] | Object pool / freelist | Часто создаваемые одинаковые объекты | Удерживает память, усложняет concurrency и очистку |
| H17 [М] | `Vec::append(&mut other)` вместо `extend(other.drain(..))` | Перемещение элементов второго вектора | Источник будет опустошён; порядок сохраняется |
| H18 [М] | `Vec::extend_from_slice` вместо поэлементного копирования | Добавление contiguous copyable данных | Для `Clone` элементов есть семантика клонирования |
| H19 [М] | `std::mem::take`, `std::mem::replace` | Переместить значение без клонирования | Должно быть корректно оставляемое значение |
| H20 [М] | Вместо `Vec<Vec<T>>` рассмотреть плоский `Vec<T>` + offsets | Много маленьких массивов | Сложнее адресация; обновления и владение |
| H21 [М] | Вместо множества `Box<T>` разместить объекты в одном `Vec<T>` | Локальность + меньше отдельных аллокаций | Перемещение элементов; устойчивость адресов и индексов |
| H22 [М] | Сократить удержание больших объектов (скопировать небольшой фрагмент при необходимости) | Память/RSS, долгоживущие срезы | Иногда осознанная малая копия выгоднее долгого удержания гигабайтного буфера |
| H23 [М] | Перенести частые выделения из цикла обработки | Разбор пакетов, временные work buffers | Сохранённый буфер должен быть очищен и не протекать между запросами |
| H24 [М] | Сравнить владение `Box<T>`, `Rc<T>`, `Arc<T>` и обычное значение | Общие данные / размер enum | `Arc` использует атомарные счётчики; `Rc` не `Send/Sync` |
| H25 [М] | Сократить частоту `Arc::clone` в горячих циклах | Очень частые атомарные refcount-op | Слишком долгий borrow способен усложнить логическую собственность |
| H26 [М] | Избегать аллокаций для временных ключей хеш-карты | `HashMap<String, V>::get(&str)` | `get` требует корректного `Borrow`/`Hash`/`Eq` для ключей |
| H27 [М] | `Vec::retain`, `retain_mut`, `dedup` вместо выделения второго контейнера | Фильтр in-place | Деструктивно меняют старый контейнер |
| H28 [М] | `shrink_to_fit` для долгоживущего сильно уменьшившегося контейнера | Нужно уменьшить удерживаемую память | Может выделять/копировать; не в горячем цикле |
| H29 [М] | Проверить размер частых enum/struct через `size_of` | Большие массивы структур | Уменьшение размера не всегда сокращает latency |
| H30 [Э] | Снижение сложности абстракций владения через арену/индексы вместо графа `Rc<RefCell<T>>` | Связанные узлы | Инвалидация индексов и новые инварианты |

**Критерий:** сравнивайте не только ns/op, но и allocations/op, bytes allocated/op и пиковую память. Для программ с короткими burst-пиками средний RSS недостаточен.

## 7. Контейнеры и структуры данных

**Коррекция редакции 2026-11-09:** в Rust `Vec<bool>` не является битовым контейнером; для экономии памяти в 8 раз требуется иной representation.

Сложность методов перечислена в [std::collections](https://doc.rust-lang.org/std/collections/index.html). Реальная производительность зависит от локальности памяти, количества объектов, распределения ключей и частот операций.

| ID | Структура/преобразование | Сильная сторона | Слабая сторона / семантика |
|---|---|---|---|
| C01 [П] | `Vec<T>` для последовательности | Локальность, компактность, итерация | Дорогие вставки/удаления в середине |
| C02 [М] | `VecDeque<T>` вместо `Vec::remove(0)` | Очередь с частыми push/pop по краям | Не всегда contiguous, больше overhead итерации |
| C03 [М] | `BinaryHeap<T>` | Очередь приоритетов, top-k | Нет сортированного последовательного обхода |
| C04 [М] | `HashMap<K, V>` | Много непоследовательных lookup | Выделение памяти, hashing, порядок обхода не фиксирован |
| C05 [М] | `BTreeMap<K, V>` | Сортированный порядок и диапазоны | Для небольших наборов зачастую избыточен |
| C06 [М] | Отсортированный `Vec<(K,V)>` | Много чтений, редкие обновления, компактный набор | `insert`/`remove` сдвигают хвост |
| C07 [М] | Обычный `Vec` + линейный поиск | Очень мало элементов | `O(n)` на один lookup |
| C08 [М] | `HashSet` vs `Vec` | Много проверок принадлежности | На малых наборах линейный поиск может быть быстрее |
| C09 [М] | Bitset для ограниченного множества небольших неотрицательных ID | Плотный домен, пересечение множеств | Размер пропорционален диапазону, не количеству элементов |
| C10 [М] | `Vec<bool>` для булевых флагов | Последовательное хранение обычных `bool` | **Не битовая упаковка**: размер `bool` — 1 байт; сравнивать с `Vec<u8>` по API/ASM, а не по воображаемой 8× экономии |
| C11 [М] | `Vec<u8>` вместо `Vec<bool>` | Когда нужны числовые 0/1 или побайтовый протокол | Оба элемента занимают 1 байт; `u8` допускает значения 2..255; для **настоящего битсета** нужен явный битовый формат / `bitvec` |
| C12 [М] | Массив `[V; N]` для малого фиксированного домена ключей | Прямой индекс | Память `O(N)`; нужно валидировать индекс |
| C13 [М] | `HashMap::entry` / `or_insert` | Убрать два поиска `contains_key`+`insert` | Учитывать стоимость создания значения: `or_insert_with` ленивее |
| C14 [М] | `HashMap::with_capacity` / `HashSet::with_capacity` | Много вставок известного размера | Излишняя память; `capacity` не равна длине |
| C15 [М][В] | Другой hasher (`ahash`, `rustc_hash`, собственный) | Доверенные целочисленные/короткие ключи | Защита от hash-flooding, порядок и воспроизводимость; внешняя зависимость |
| C16 [М] | Предвычислить индекс ключей / ID, использовать `usize` | Повторные обращения к строковым ключам | Нужна согласованная таблица соответствия |
| C17 [М][В] | `Vec::swap_remove(index)` вместо `remove(index)` | Ненужен порядок элементов | **Меняет порядок**: на место удаления ставится последний элемент |
| C18 [М] | `Vec::retain` вместо удаления внутри цикла по индексу | Отбор большого числа элементов | Семантика сохранения порядка у `retain`; сдвиги всё равно возможны |
| C19 [М] | `Vec::dedup` после сортировки | Удаление соседних дублей | Без сортировки удаляет только последовательные дубли |
| C20 [М][В] | `sort_unstable` вместо `sort` | Стабильность равных элементов не важна | **Меняет порядок эквивалентных ключей**, не всегда быстрее |
| C21 [М] | `sort_unstable_by_key` / `sort_by_cached_key` — сравнить | Дорогие ключи сортировки | `sort_by_cached_key` выделяет память, ключ может измениться |
| C22 [М] | `select_nth_unstable` вместо полного `sort` | Нужно k-е число или разделение по порядку | Деструктивно переставляет коллекцию |
| C23 [М] | `partition_point` / `binary_search` | Уже отсортированные данные | Предикат должен задавать монотонное разделение |
| C24 [М] | `BTreeMap::range` | Сканировать ключи на отрезке | Требует полного порядка и логики диапазонов |
| C25 [М] | `Vec::split_off`, `drain`, `splice` | Управление частями вектора | Могут перемещать много элементов/выделять память |
| C26 [М] | `HashMap::retain` | Фильтрация словаря на месте | Стоимость зависит от размера таблицы, не только числа живых элементов |
| C27 [М] | `LinkedList` только когда свойства узлов действительно нужны | O(1) append двух списков | Аллокации узлов и плохая локальность почти всегда мешают обычным задачам |
| C28 [Э] | Open addressing, Robin Hood, специализированные hash tables — внешние crates | Очень специфические профили ключей | Security/API/comparability; нужно сравнивать с `std` |
| C29 [М] | Предпочесть id/arena graph множеству узлов на куче | Обход графов, locality | Нужны стабильные индексы, отдельное хранение ссылок |
| C30 [М] | Выбрать плотную либо разреженную матрицу | Sparse данные | Порог зависит от плотности, доступа и операций |

**Безопасность:** стандартный `HashMap` использует случайно инициализируемый hasher с защитой от HashDoS; конкретный алгоритм — внутренняя деталь и может меняться. Подмена на незащищённый быстрый hasher допустима только после оценки входов. [std::HashMap](https://doc.rust-lang.org/std/collections/struct.HashMap.html).

## 8. Строки, UTF-8 и парсинг

**Ключевой контракт:** `String` и `&str` — UTF-8. Индекс по байтам **не является** индексом по Unicode-символам; `chars()` возвращает Unicode scalar values, а не пользовательские grapheme clusters. ASCII-оптимизации применимы только к явно ASCII-домену или с соответствующим fallback.

| ID | Приём | Где полезен | Когда опасен или бесполезен |
|---|---|---|---|
| S01 [П] | Принимать `&str`, если владение не требуется | Функции анализа и поиска | Нельзя сохранять за время жизни владельца |
| S02 [П] | `&[u8]` для бинарных протоколов | Бинарный парсинг, сетевые сообщения | Не изображать бинарные данные как UTF-8 |
| S03 [П] | `str::split_once`, `split_whitespace`, `lines` без промежуточных `String` | Парсинг небольших форматов | Особенности delimiter, Unicode whitespace и CRLF |
| S04 [П] | Избегать `split(...).collect::<Vec<_>>()`, когда нужен только первый фрагмент | Токенизация | Если несколько проходов по токенам, материализация может быть выгодной |
| S05 [М] | `str::find` / `contains` вместо ручного char-loop | Поиск разделителей | Требуется тот же вид сопоставления: byte, char, substring |
| S06 [М] | Поиск фиксированного байта по `as_bytes()` | ASCII протоколы | `as_bytes` безопасен; возвращаемые диапазоны должны совпадать с границами UTF-8 при срезе `str` |
| S07 [М] | `memchr`/`memmem` — внешний crate | Много поиска байтов/подстрок | Бинарная семантика и версия библиотеки |
| S08 [П] | `push_str`, `push`, `write!(&mut String, ...)` вместо серии `format!` | Формирование текста в цикле | Считать число аллокаций; `write!` форматирует значения, не бесплатен |
| S09 [П] | `String::with_capacity` | Приблизительно известен размер результата | Перебор capacity удерживает память |
| S10 [П] | Переиспользовать `String::clear()` | Построчные операции | Требуется убрать ссылки на старое содержимое |
| S11 [М] | Использовать `str::parse::<u64>()` без `String` из токена | Парсинг чисел | Ошибки разбора, знаки, overflow сохранять |
| S12 [М][В] | Специализированный парсер ASCII-десятичных чисел | Формат известен и фиксирован | Учитывать `+`, минус, пробелы, leading zeros, overflow, пустые данные |
| S13 [М] | `std::fmt::Write` в существующий `String` | Повторное форматирование | Не путать с `std::io::Write` |
| S14 [М] | `std::io::Write` в `Vec<u8>` | Сборка бинарных пакетов | Ошибки записи даже у универсального интерфейса нужно корректно обрабатывать |
| S15 [М] | Избегать `.to_lowercase()` для сравнений, где достаточно ASCII-case | HTTP-подобные ASCII идентификаторы | Unicode case folding отличается от ASCII и может менять длину |
| S16 [В] | `eq_ignore_ascii_case` вместо Unicode-нормализации | Контракт **только ASCII** | Не эквивалентно полному Unicode case-insensitive сравнению |
| S17 [М] | `String` → `Box<str>` если строка неизменна | Большое число постоянных строк | Нельзя дописывать; возможна реаллокация при преобразовании |
| S18 [М] | Interning строк / перевод в числовые ID | Множество повторяющихся одинаковых ключей | Таблица интернирования удерживает память, нужно управление сроком жизни |
| S19 [М] | Парсить на срезах исходного буфера | Краткоживущие токены | Нельзя освободить/перезаписать исходный буфер раньше потребителя |
| S20 [М] | Склеивать строки за один проход вместо цепочки `a + b + c` | Многие мелкие куски | Стоимость данных важнее синтаксиса; `concat` может быть оптимизирован |
| S21 [Э][В] | SIMD-парсер цифр, JSON/CSV — внешние crates | Очень большие однородные потоки | Контракт ошибок, Unicode, даты, escape и формат |
| S22 [П] | Учитывать цену UTF-8 декодирования, но не удалять Unicode | Текстовые pipelines | Пропуск не-ASCII символов — изменение результата |
| S23 [М] | Передавать `&Path` вместо `PathBuf` | Функции чтения путей | `Path` не обязан быть UTF-8, нельзя бездумно приводить к `str` |
| S24 [М] | Избегать повторного регулярного выражения/парсера на строку | Лог-обработка, разбор шаблонов | Regex требует внешний crate, инициализация/кеш тоже имеют стоимость |

| I14 [М] | Снизить частоту `fsync`/`flush` только при допустимом контракте надёжности | Хранилища/журналы | **Меняет гарантию долговечности данных** |

## 10. Циклы, итераторы и проверки границ

| ID | Приём | Типичный эффект | Ограничение |
|---|---|---|---|
| L01 [П] | `for item in &slice` вместо `for i in 0..slice.len()` | Проще устранение bounds checks | У индексов бывают необходимые связи между массивами |
| L02 [М] | `zip` двух срезов | Меньше сложной индексации | **Останавливается на кратчайшем срезе**, проверьте длины |
| L03 [М] | `chunks_exact(k)` | Блочная обработка известного размера | Хвост нужно обработать отдельно через `remainder()` |
| L04 [М] | `as_chunks::<N>()` | Компилятор видит размер статического блока | Нужно обработать остаток; избегать ошибочного полного игнорирования хвоста |
| L05 [М] | `split_at`, `split_at_mut` | Независимые подмассивы с доказанной непересекаемостью | Проверка границы split; неверная логика разделения меняет результат |
| L06 [М] | `iter_mut` вместо повторных обращений по индексу | Внутренние мутации | Borrow checker может потребовать реструктуризации |
| L07 [М] | Вынести `len`, конфигурацию, индексы таблиц и чистые расчёты из цикла | Инвариантные выражения | LLVM часто делает это автоматически |
| L08 [М] | `any`, `all`, `find`, `position` вместо полной обработки | Возможно раннее завершение | Порядок побочных эффектов может измениться |
| L09 [М] | `filter_map` / `flat_map` без промежуточных Vec | Pipeline обработки | Слияние циклов может ухудшить locality/parallelism |
| L10 [М] | `fold`/`sum`/`product` вместо ручных temporary containers | Свёртки | Переполнение и порядок вычислений сохранить явно |
| L11 [М] | Сократить число условных ветвей в горячем цикле | Непредсказуемые ветки | Branchless код может выполнять больше работы |
| L12 [М] | `if` перенести за цикл, если он инвариантен | Горячие циклы | Дублирует код, может увеличить instruction cache pressure |
| L13 [М] | Несколько независимых аккумуляторов | Зависимая цепочка сложений/умножений | Изменение порядка для float меняет округление |
| L14 [М] | Ручная развёртка | Крайне короткие tight loops | LLVM уже разворачивает; растёт код и регистровое давление |
| L15 [М] | Упрощать доступ и aliasing для авто-SIMD | Многочисленные однотипные элементы | Не всякий LLVM автоматически векторизует |
| L16 [М] | Предпроверка длины / срез до цикла | Доказательство инвариантов bounds | Паника/условие ошибки должны оставаться корректными |
| L17 [Э] | `get_unchecked` / `get_unchecked_mut` | Только доказанный hotspot с неустранимыми проверками | **UB при неверных индексах; никакого `unsafe` ради косметики** |
| L18 [М] | `enumerate` при необходимости индекса вместе с элементом | Читаемость и часто хороший ASM | Нет гарантии превосходства по производительности |
| L19 [М] | Изменить порядок вложенных циклов | Матрицы, локальность | Нужно учитывать row/column layout и зависимость вычислений |
| L20 [М] | Loop tiling/cache blocking | Крупные многомерные массивы | Подбирать блок под кэш/ядро/тип данных |
| L21 [М] | Однопроходная фильтрация in-place | Сокращение копий | Меняет исходную коллекцию |
| L22 [М] | `scan` вместо отдельной накопительной коллекции | Префиксная обработка | Дополнительная логика итератора может усложнить оптимизации |
| L23 [М] | `take_while`/`skip_while` для монотонных данных | Досрочная остановка или пропуск | Нельзя пропускать данные по неверному условию |
| L24 [М] | Проверить генерацию ASM до ручной микрооптимизации | Узкие внутренние циклы | ISA и компилятор влияют сильнее исходного стиля |
| L25 [Э] | Raw pointers и `unsafe` обходы | Только профилируемые случаи с доказанными инвариантами | Lifetime, aliasing, provenance, UB, тяжёлая поддержка |

`slice::as_chunks::<N>()` и `as_chunks_mut` доступны в **stable Rust с 1.88.0**; при более старом MSRV используйте `chunks_exact` и обработку хвоста.

`zip` **не** является эквивалентом индексированного цикла, если длины различаются. `chunks_exact` не обрабатывает хвост сам по себе. Безопасные методы устранения проверок границ подробно разобраны в [Performance Book — Bounds Checks](https://nnethercote.github.io/perf-book/bounds-checks.html). Для блоков массивов см. [std::slice](https://doc.rust-lang.org/std/primitive.slice.html).

## 11. Кэш процессора и представление данных

| ID | Приём | Когда помогает | Когда не помогает / риск |
|---|---|---|---|
| D01 [П] | Последовательный проход по `Vec`/slice | Большие наборы данных | Если алгоритм по сути случайный доступ |
| D02 [М] | Structure of Arrays (SoA) вместо Array of Structures (AoS) | Читаются только 1–2 поля многих записей | Дорогая перестройка, хуже локальность обработки записи целиком |
| D03 [М] | AoS вместо SoA | Каждый проход использует большинство полей одной записи | Может мешать SIMD и расточать memory bandwidth |
| D04 [М] | Сжимать типы, enum/struct, измеряя `size_of` | Множество записей | `size_of` — ещё не измерение производительности |
| D05 [Э] | Менять порядок полей при `#[repr(C)]` | Совместимый с ABI тип, большие padding | **У обычного `repr(Rust)` порядок полей не гарантирован**, не полагаться на текстовый порядок |
| D06 [М] | Горячие поля отдельно от холодных (hot/cold split) | Частый доступ к небольшой части | Дополнительная косвенность при холодных обращениях |
| D07 [М] | Индексы вместо разрозненных heap-указателей | Графы, AST, деревья, game ECS | Нужна стратегия invalidation/compact storage |
| D08 [М] | Cache blocking для матриц | Превышение кэша L1/L2 | На маленьких матрицах только добавит циклы |
| D09 [М] | Контроль false sharing (паддинг независимых счётчиков) | Несколько потоков изменяют соседние cache lines | `#[repr(align(64))]` увеличивает память, 64B — не универсальная линия |
| D10 [М] | Уменьшить случайные переходы по памяти | Hash tables, pointer-heavy trees | Иногда структура данных диктуется задачей |
| D11 [М] | Снизить число байт на объект | Сквозная обработка миллионов записей | Узкий тип может переполниться и изменить семантику |
| D12 [Э] | Prefetch интринсиками | Предсказуемый, достаточно удалённый доступ | Обычный CPU prefetcher часто лучше ручного; может засорить кэш |
| D13 [М] | Не держать гигантские временные массивы одновременно | Пиковый RSS и страничные ошибки | Могут понадобиться повторные вычисления |
| D14 [М] | Переиспользовать память без лишних копий | Конвейеры обработки | Дольше удерживается память, могут появиться race/ownership сложности |
| D15 [М] | Сравнить `Box<[T]>` / плоский `Vec<T>` с `Vec<Box<T>>` | Массивы объектов | Устойчивые адреса и полиморфизм требуют других структур |
| D16 [М] | Специальное компактное представление common values | Много повторов и редких исключений | Кодек/декодек и ветвления могут дорого стоить |
| D17 [М] | Избегать лишнего `memcpy` и больших перемещаемых значений | Большие structs | Иногда копия дешевле уровня косвенности |
| D18 [Э] | NUMA-aware размещение/first-touch | Многосокетные сервера и объёмы > LLC | Платформозависимо; неверная привязка ухудшит работу |

**Осторожно с `#[repr(packed)]`:** оно не является общим средством ускорения. Невыровненные поля могут требовать медленного доступа; взятие обычных ссылок на такие поля недопустимо без специальных правил. См. [Rustonomicon — repr(Rust)](https://doc.rust-lang.org/nomicon/repr-rust.html), [Performance Book — Type Sizes](https://nnethercote.github.io/perf-book/type-sizes.html).

**Memory ordering:** `Relaxed` гарантирует атомарность отдельного обращения, но **не** публикацию других данных и не `happens-before`. Для передачи готового сообщения между потоками часто нужны Acquire/Release, блокировки или каналы. См. [Atomic Ordering](https://doc.rust-lang.org/core/sync/atomic/enum.Ordering.html) и [Rustonomicon — Atomics](https://doc.rust-lang.org/nomicon/atomics.html).

### Три разных ответа на переполнение

```rust
fn checked_sum(a: u32, b: u32) -> Option<u32> {
    a.checked_add(b)
}

fn modular_sum(a: u32, b: u32) -> u32 {
    a.wrapping_add(b)
}

fn capped_sum(a: u32, b: u32) -> u32 {
    a.saturating_add(b)
}
```

Ни один из вариантов не является универсально «самым быстрым и правильным». Он должен соответствовать математическому контракту. Обычный `+` при переполнении зависит от настроек проверки переполнения и может вызвать панику; `wrapping_add` точно задаёт модульную арифметику во всех профилях.

## 19. Практические примеры «до / после»

Примеры написаны самостоятельно по общим идеям из документации. Здесь слово «после» означает **кандидат на оптимизацию**, а не обещание скорости. Там, где контракт изменился, это прямо отмечено. Фрагменты независимы, не представляют собой один компилируемый файл.

### 19.1. Известная длина вектора: резервировать вместимость

```rust
// До: вектор может неоднократно расти
fn copy_values_before(input: &[u64]) -> Vec<u64> {
    let mut output = Vec::new();
    for &value in input {
        output.push(value);
    }
    output
}

// После: верхняя граница размера заранее известна
fn copy_values_after(input: &[u64]) -> Vec<u64> {
    let mut output = Vec::with_capacity(input.len());
    for &value in input {
        output.push(value);
    }
    output
}
```

**Триггер:** большой предсказуемый объём `push`. **Риск:** если `input` часто пустой, обе версии обычно не выделяют память; если объём лишь оценочный, большая capacity иногда тратит RAM. **Дополнительно:** для этого частного случая `input.to_vec()` может быть проще и эффективнее обоих циклов.

### 19.2. Повторное использование буфера между вызовами

```rust
// До: в каждом вызове создаётся новый объект-буфер
fn make_payload_before(values: &[u8]) -> Vec<u8> {
    let mut result = Vec::new();
    result.extend_from_slice(values);
    result
}

// После: вызывающий хранит буфер между обработками
fn write_payload_after(values: &[u8], buffer: &mut Vec<u8>) {
    buffer.clear();
    buffer.extend_from_slice(values);
}
```

**Триггер:** повторные партии схожего размера. **Внимание:** API **изменён**: вторая функция ничего не возвращает, а перезаписывает внешний буфер. Для эквивалентности вызывающий должен сравнивать полученное содержимое после каждого вызова.

### 19.3. Не клонировать строку ради поиска

```rust
use std::collections::HashMap;

// До
fn lookup_before(map: &HashMap<String, usize>, key: &str) -> Option<usize> {
    map.get(&key.to_owned()).copied()
}

// После
fn lookup_after(map: &HashMap<String, usize>, key: &str) -> Option<usize> {
    map.get(key).copied()
}
```

**Триггер:** `HashMap<String, _>` и временный `String` для `get`. **Почему:** реализация `Borrow<str>` позволяет искать по `&str` без выделения. **Контракт:** идентичен при одинаковых ключах.

### 19.4. Одна проверка ключа через `entry`

```rust
use std::collections::HashMap;

fn count_before(values: &[u32]) -> HashMap<u32, usize> {
    let mut counts = HashMap::new();
    for &value in values {
        if counts.contains_key(&value) {
            if let Some(count) = counts.get_mut(&value) {
                *count += 1;
            }
        } else {
            counts.insert(value, 1);
        }
    }
    counts
}

fn count_after(values: &[u32]) -> HashMap<u32, usize> {
    let mut counts = HashMap::new();
    for &value in values {
        *counts.entry(value).or_insert(0) += 1;
    }
    counts
}
```

**Триггер:** повторные обращения по одному ключу. **Контракт:** обе версии используют обычное `usize` сложение, то есть одинаковые настройки overflow checks. В обычном коде учтите реальную возможность переполнения счётчика.

### 19.5. Удаление с начала: очередь, а не сдвиг массива

```rust
use std::collections::VecDeque;

// До
fn process_before(values: &[u32]) -> u64 {
    let mut queue = values.to_vec();
    let mut result = 0_u64;
    while !queue.is_empty() {
        result += u64::from(queue.remove(0));
    }
    result
}

// После
fn process_after(values: &[u32]) -> u64 {
    let mut queue: VecDeque<_> = values.iter().copied().collect();
    let mut result = 0_u64;
    while let Some(value) = queue.pop_front() {
        result += u64::from(value);
    }
    result
}
```

**Триггер:** частая операция с головой очереди. **Когда не нужно:** если вы просто хотите пройти массив один раз, самый простой вариант — `values.iter().map(|&x| x as u64).sum()`, без создания **любой** очереди.

### 19.6. Один проход без промежуточного контейнера

```rust
fn even_sum_before(values: &[u64]) -> u64 {
    let evens: Vec<_> = values.iter().copied().filter(|x| x % 2 == 0).collect();
    evens.iter().copied().fold(0, u64::wrapping_add)
}

fn even_sum_after(values: &[u64]) -> u64 {
    values.iter()
        .copied()
        .filter(|x| x % 2 == 0)
        .fold(0, u64::wrapping_add)
}
```

**Триггер:** промежуточная коллекция не используется повторно. **Важно:** `fold(0, u64::wrapping_add)` явно сохраняет модульное переполнение в обеих версиях.

### 19.7. Потенциальный конец раньше начала: ранний выход

```rust
fn has_target_before(values: &[u32], target: u32) -> bool {
    values.iter().filter(|&&x| x == target).count() != 0
}

fn has_target_after(values: &[u32], target: u32) -> bool {
    values.contains(&target)
}
```

**Триггер:** элемент часто обнаруживается до конца последовательности. **Контракт:** для обычного `u32` тот же результат. **Примечание:** для пользовательских типов с побочными эффектами в сравнении сокращение числа сравнений может быть заметным изменением.

### 19.8. Токены: найти один разделитель без создания вектора

```rust
fn kv_before(input: &str) -> Option<(&str, &str)> {
    let parts: Vec<_> = input.splitn(2, '=').collect();
    match parts.as_slice() {
        [key, value] => Some((key, value)),
        _ => None,
    }
}

fn kv_after(input: &str) -> Option<(&str, &str)> {
    input.split_once('=')
}
```

**Триггер:** нужен только первый `=`. **Контракт:** обе версии возвращают разделённые срезы без копирования текста. `split_once` корректно отдаёт `""` для пустой части.

### 19.9. Построчное чтение: reusable `String`

```rust
use std::io::{self, BufRead};

fn count_before<R: BufRead>(reader: R) -> io::Result<usize> {
    let mut count = 0;
    for line in reader.lines() {
        let _line = line?;
        count += 1;
    }
    Ok(count)
}

fn count_after<R: BufRead>(mut reader: R) -> io::Result<usize> {
    let mut line = String::new();
    let mut count = 0;
    while reader.read_line(&mut line)? != 0 {
        count += 1;
        line.clear();
    }
    Ok(count)
}
```

**Триггер:** тысячи строк, нужно прочитать их без хранения всех одновременно. **Контракт:** здесь только подсчёт строк; если нужен сам текст, `lines()` удаляет терминатор строки, а `read_line()` оставляет его внутри `String` — привести к одной семантике перед заменой.

### 19.10. Однократная блокировка стандартного вывода

```rust
use std::io::{self, Write};

fn print_before(values: &[u32]) -> io::Result<()> {
    for value in values {
        writeln!(io::stdout(), "{value}")?;
    }
    Ok(())
}

fn print_after(values: &[u32]) -> io::Result<()> {
    let stdout = io::stdout();
    let mut output = stdout.lock();
    for value in values {
        writeln!(output, "{value}")?;
    }
    output.flush()
}
```

**Триггер:** частые операции вывода. **Контракт/риск:** одновременный вывод других потоков будет сериализован на более крупной области; это может **изменить interleaving** сообщений.

### 19.11. Избавиться от O(n²) удаления по индексу

```rust
fn keep_even_before(values: &mut Vec<u32>) {
    let mut index = 0;
    while index < values.len() {
        if values[index] % 2 != 0 {
            values.remove(index);
        } else {
            index += 1;
        }
    }
}

fn keep_even_after(values: &mut Vec<u32>) {
    values.retain(|value| value % 2 == 0);
}
```

**Триггер:** из большого `Vec` выбрасывается много элементов. **Контракт:** сохраняется относительный порядок оставшихся значений.

### 19.12. `swap_remove`: только если порядок не важен

```rust
fn remove_before(values: &mut Vec<u64>, index: usize) -> u64 {
    values.remove(index)
}

fn remove_after(values: &mut Vec<u64>, index: usize) -> u64 {
    values.swap_remove(index)
}
```

**Триггер:** контейнер — неупорядоченный набор. **ОБЯЗАТЕЛЬНО:** `behavior_change = "order"`: два вызова возвращают удалённый элемент, но оставшийся порядок **может отличаться**. Для очереди задач/временного ряда это неэквивалентно.

### 19.13. `chunks_exact`: обработать хвост

```rust
// Никакого unsafe. Пример считает пары и оставляет одиночный хвост.
fn pairwise_sum(values: &[u64]) -> (Vec<u64>, Option<u64>) {
    let mut chunks = values.chunks_exact(2);
    let pairs = chunks
        .by_ref()
        .map(|pair| pair[0].wrapping_add(pair[1]))
        .collect::<Vec<_>>();
    let tail = chunks.remainder().first().copied();
    (pairs, tail)
}
```

**Триггер:** регулярные блоки из 2/4/8 элементов. **Риск:** не забывать хвост и точную семантику переполнения.

### 19.14. `zip` с явным контрактом одинаковой длины

```rust
fn dot_equal_length(a: &[u64], b: &[u64]) -> Option<u64> {
    if a.len() != b.len() {
        return None;
    }
    Some(
        a.iter()
            .zip(b)
            .fold(0_u64, |sum, (&x, &y)| sum.wrapping_add(x.wrapping_mul(y))),
    )
}
```

**Триггер:** связанные массивы одинаковой длины. **Контракт:** без предварительной проверки `zip` молча игнорировал бы хвост длинного массива; это **не** замена индексации с обязательной равной длиной.

### 19.15. Только медиана: не сортировать весь массив

```rust
fn median_before(values: &[i64]) -> Option<i64> {
    if values.is_empty() { return None; }
    let mut data = values.to_vec();
    data.sort_unstable();
    Some(data[data.len() / 2])
}

fn median_after(values: &[i64]) -> Option<i64> {
    if values.is_empty() { return None; }
    let mut data = values.to_vec();
    let position = data.len() / 2;
    let (_, median, _) = data.select_nth_unstable(position);
    Some(*median)
}
```

**Триггер:** нужна верхняя медиана (`len/2`), порядок прочих элементов не нужен. **Риск:** возвращать **пару средних** для чётной длины — другая задача, её алгоритм надо определить отдельно.

### 19.16. `HashSet` малых целых → битовая маска

```rust
use std::collections::HashSet;

fn unique_before(values: &[u8]) -> usize {
    values.iter().copied().collect::<HashSet<_>>().len()
}

fn unique_after(values: &[u8]) -> usize {
    let mut seen = [false; 256];
    let mut unique_count = 0;
    for &value in values {
        let slot = &mut seen[usize::from(value)];
        if !*slot {
            *slot = true;
            unique_count += 1;
        }
    }
    unique_count
}
```

**Триггер:** известный плотный домен `u8`. **Риск:** для случайных `u64` подобный массив создать нельзя без иной стратегии; при очень малых объёмах разница может отсутствовать.

### 19.17. Построение текста: избегать `format!` для каждого значения

```rust
use std::fmt::Write as _;

fn join_before(values: &[u32]) -> String {
    let mut out = String::new();
    for &value in values {
        out.push_str(&format!("{value};"));
    }
    out
}

fn join_after(values: &[u32]) -> String {
    let mut out = String::new();
    for &value in values {
        write!(&mut out, "{value};").expect("writing to String cannot fail");
    }
    out
}
```

**Триггер:** частые `format!`/`push_str`. **Контракт:** обе версии возвращают `String` и одинаковый текст; `fmt::Write` для `String` не должен возвращать `fmt::Error`. Ошибку не скрываем молча, а оформляем `expect` с объяснением.

### 19.18. Возвращать срез вместо обязательной копии

```rust
fn get_prefix_before(input: &str) -> String {
    input.split_once(':').map_or(input, |(prefix, _)| prefix).to_owned()
}

fn get_prefix_after(input: &str) -> &str {
    input.split_once(':').map_or(input, |(prefix, _)| prefix)
}
```

**Триггер:** пользователю функции достаточно `&str`. **Контракт:** функция теперь возвращает заимствование; это осознанное **изменение API/lifetime**, не drop-in replacement.

### 19.19. Инициализация один раз через `LazyLock`

```rust
use std::sync::LazyLock;

static PRECOMPUTED: LazyLock<Vec<u64>> = LazyLock::new(|| {
    (0..1000_u64).map(|n| n * n).collect()
});

fn look_up(index: usize) -> Option<u64> {
    PRECOMPUTED.get(index).copied()
}
```

**Триггер:** таблица создаётся дорого и используется повторно. **Когда не нужно:** если таблица редко нужна либо стоит дешево построить, ленивая инициализация может добавить сложность. `LazyLock` синхронизируется между потоками; паника внутри инициализации приводит к отравлению.

### 19.20. Специализация кодовой ветви под ASCII (с fallback)

```rust
fn ascii_or_unicode_letters(input: &str) -> usize {
    if input.is_ascii() {
        input.as_bytes().iter().filter(|&&b| b.is_ascii_alphabetic()).count()
    } else {
        input.chars().filter(|character| character.is_alphabetic()).count()
    }
}
```

**Триггер:** большинство входов — ASCII, нужен учёт Unicode-букв на остальных. **Риск:** результаты для некоторых не-ASCII символов зависят от Unicode tables; это не grapheme counting. Не заменяйте Unicode branch на удаление не-ASCII символов.

### 19.21. Реально необходимое удаление по готовому условию

```rust
fn filter_records(values: &mut Vec<i32>, minimum: i32) {
    values.retain(|value| *value >= minimum);
}
```

Это пример оптимизации in-place без второго вектора. **Не** эквивалентно `values.iter().filter(...).collect::<Vec<_>>()`, если вызывающему нужно сохранить исходный контейнер; контракт владения изменён.

### 19.22. Вне цикла: проверить CPU feature один раз

```rust
#[cfg(target_arch = "x86_64")]
fn cpu_path_name() -> &'static str {
    if std::arch::is_x86_feature_detected!("avx2") {
        "avx2"
    } else {
        "scalar"
    }
}
```

**Пояснение:** это лишь **диспетчер**, а не реализация SIMD-ядра. Реальную функцию с `#[target_feature(enable = "avx2")]` вызывайте только после доказанной проверки возможностей. При включении `target-cpu=native` портативность бинарника ограничена ещё на этапе компиляции.

### 19.23. Параллелизм — только крупные работы

```rust
use std::thread;

fn parallel_sums(left: &[u64], right: &[u64]) -> thread::Result<(u64, u64)> {
    thread::scope(|scope| {
        let handle = scope.spawn(|| {
            left.iter().copied().fold(0_u64, u64::wrapping_add)
        });
        let right_sum = right.iter().copied().fold(0_u64, u64::wrapping_add);
        let left_sum = handle.join()?;
        Ok((left_sum, right_sum))
    })
}
```

**Контракт:** ошибки `join()` не замалчиваются: возвращается `thread::Result`. Для маленьких массивов создание потока часто стоит дороже всей арифметики. Для производственного кода используйте пул потоков и измеряйте порог размера задачи.

### 19.24. Избыточная синхронизация: локальный накопитель

```rust
use std::sync::Mutex;

fn add_values_fine_grained(mutex: &Mutex<u64>, data: &[u64]) {
    for &value in data {
        if let Ok(mut counter) = mutex.lock() {
            *counter = counter.wrapping_add(value);
        }
    }
}

fn add_values_batched(mutex: &Mutex<u64>, data: &[u64]) {
    let delta = data.iter().copied().fold(0_u64, u64::wrapping_add);
    if let Ok(mut counter) = mutex.lock() {
        *counter = counter.wrapping_add(delta);
    }
}
```

**Триггер:** очень частые блокировки одного счётчика. **Изменение контракта:** другие потоки теперь увидят обновление пакетом вместо промежуточных значений; может измениться очередь конкуренции и поведение ошибок lock poison. Применять только если агрегирование допускает такую видимость.

## 20. Ошибочные «оптимизации» и семантические ловушки

Здесь важно различать **медленный, но корректный вариант** и **быстрый, но неправильный вариант**. Первый иногда допустим; второй — дефект. Без профиля нельзя обещать скорость, но часть нарушений поведения можно установить логически и тестами.

| Плохое решение | Почему обычно плохо | Что делать вместо |
|---|---|---|
| Создавать новый `Vec` в каждом элементе цикла | Лишние выделения/копирование | Рабочий reusable buffer или прямой проход |
| `values.to_vec()[i]` для получения одного элемента | Полное копирование ради чтения | `values[i]` или `values.get(i)` |
| Строить `HashMap` внутри каждого lookup | Повторное создание индекса | Построить один раз за партию или искать линейно при малом размере |
| Строить `BTreeMap` ради одного прохода без сортировки | `O(n log n)` и выделения | `Vec` и прямой проход |
| `format!` на каждый элемент перед `push_str` | Временные строки и аллокации | `write!` в готовый `String` |
| `clone()` большого `Vec` ради одного чтения | Копия всех элементов | Срез/ссылка |
| `Arc::clone` десятки тысяч раз без реальной потребности | Атомарные операции refcount | Передавать ссылку на срок работы там, где допустимо |
| `Mutex` lock/unlock на каждый элемент | Синхронизация доминирует вычисление | Локальный accumulator + один lock, **если семантика позволяет** |
| `std::thread::spawn` на каждый маленький элемент | Создание и переключение потоков | Пул и крупные партии |
| `SmallVec` для большинства длинных векторов | Дополнительная ветка/размер объекта | Сравнить с обычным `Vec` |

### Контракт, который обязательно проверять при ревью

- **Значения:** результат на пустых/малых/максимальных входах; нули, NaN, бесконечность, отрицательные и `u64::MAX`.
- **Порядок:** стабильность сортировки, порядок обхода `HashMap`, наблюдаемое промежуточное состояние и вывод из потоков.
- **Ошибки:** тот же `Option`/`Result`, та же ветка overflow, отказ чтения/записи, ошибки валидации.
- **Память:** время жизни возвращаемых срезов, адресная стабильность, peak RSS, число аллокаций, возможные новые блокировки.
- **Конкуренция:** `Send`/`Sync`, границы критической секции, memory ordering, fair scheduling и visibility.
- **Платформы:** MSRV, target triple, CPU features, filesystem/endianness/FFI.
- **Точность:** float epsilon/ULP, детерминизм, изменение порядка свёрток, аппроксимации.

## 21. Диагностика: что менять по симптомам

| Симптом в профиле | В первую очередь посмотреть | Кандидаты из каталога |
|---|---|---|
| `malloc`, `free`, `realloc` горячие | Число и места аллокаций; `clone`, `format!` | H01–H30, S08–S10, I04 |

| Много `branch-misses` | Граница fast path, зависимость от входа | A12, A18, L11–L12, PGO |
| Время в `HashMap`/`HashSet` | Ключи, размер домена, количество проходов | C04–C16, H26 |
| Время в `sort` | Нужна ли полная сортировка и стабильность | A13–A14, C20–C23 |
| Время в `Mutex::lock`/`futex` | Частота lock и длительность секций | P05–P19, X06–X08 |
| `write`/`read` syscalls часто | Буферизация и размер batch | I01–I10 |
| p99 значительно хуже p50 | Очереди, длинные блокировки, аллокации, GC сторонних систем | P04–P20, X01–X17 |

| Все CPU заняты, throughput не растёт | Память/NUMA/контеншн/частоты CPU | D01–D18, P04–P24 |
| Огромный бинарник | Мономорфизация, features, strip, LTO | G01–G14, T01–T15 |
| Сборка слишком долгая | Proc macros, LLVM IR, linker | B12, B16–B20, T05–T14 |
| Упор в арифметику плотного массива | LLVM ASM, авто-SIMD, CPU ISA | L13–L16, V01–V18, N01–N22 |
| Код «сложный, но не быстрее» | Избыточная специализация и `unsafe` | Разделы 1–4, 20, откат правки |

### Пять быстрых гипотез, если нет времени на глубокий анализ

1. Выполняется ли **реально** релизная сборка?
2. Не делается ли `clone`/`format!`/новая коллекция **внутри самого частого цикла**?
3. Подходит ли контейнер: `Vec`, `VecDeque`, `HashMap`, `BTreeMap`?
4. Не выполняется ли один и тот же поиск/разбор/сортировка много раз?
5. Не вызывает ли «ускоряющая» параллельность лишние блокировки/распределение задач?

Если все пять пунктов исключены — переходите к профилированию ASM, кэша и численной части. Без них микрооптимизация чаще превращается в угадывание.

## 24. Что конкретно видно в двух видео и какие выводы из этого делать

### 24.1. `videoplayback.mp4` (~4:58): копировать заказы до сортировки или после?

На экране демонстрируется функция `recent_orders`: фильтрация заказов определённого клиента, сортировка по времени и ограничение числа результатов. В сравнении показаны варианты с копированием заказов **до** выбора нужных результатов и с работой по ссылкам до момента, когда результат сформирован. Ближе к 04:00 на экране есть две медианы бенчмарка, но их нельзя переносить на другой код и оборудование без воспроизведения условий.

**Гипотеза для проверки:** если `Order` содержит большой `String` или другой дорогой в клонировании payload, сортировать и отбирать `&Order`, а клонировать только вошедшие в результат объекты. Это уменьшает работу на всех отфильтрованных, но отброшенных позже заказах.

```rust
#[derive(Clone)]
struct Order {
    customer_id: u32,
    created_at: u64,
    note: String,
}

// До: клонируются все подходящие заказы, в том числе не вошедшие в top N.
fn orders_before(orders: &[Order], customer_id: u32, limit: usize) -> Vec<Order> {
    let mut selected: Vec<Order> = orders.iter()
        .filter(|order| order.customer_id == customer_id)
        .cloned()
        .collect();
    selected.sort_by(|left, right| right.created_at.cmp(&left.created_at));
    selected.truncate(limit);
    selected
}

// После: ссылки сортируются, а клонируются лишь объекты в итоговом наборе.
fn orders_candidate(orders: &[Order], customer_id: u32, limit: usize) -> Vec<Order> {
    let mut selected: Vec<&Order> = orders.iter()
        .filter(|order| order.customer_id == customer_id)
        .collect();
    selected.sort_by(|left, right| right.created_at.cmp(&left.created_at));
    selected.truncate(limit);
    selected.into_iter().cloned().collect()
}
```

**Контракт:** обе версии сохраняют стабильность сортировки для равного `created_at`. Если заменить `sort_by` на `sort_unstable_by`, результат при одинаковых датах может измениться. Результат всё ещё **владеет** заказами; если API может возвращать `Vec<&Order>`, можно отказаться и от финальных клонов, но это изменение публичного контракта и времени жизни ссылок. Плохой сценарий для нового варианта: `Order` дешевле скопировать, чем косвенно обращаться к нему через ссылки; тогда сортировка указателей может проигрывать.

**Эксперимент:** сравнить долю подходящих заказов 1%, 50%, 100%; `limit = 0, 1, 20, 20_000`; короткие и длинные строки; одинаковые временные метки; объём данных выше LLC; количество аллокаций и p95 задержку.

### 24.2. `18 минут ЧИСТЕЙШЕГО БЛЭЙЗИНГА...mp4` (~18:15): `enum Event`, `Tick`, `String`, `match`, chunks

В кадрах видна задача обработки порядка миллионов событий `Event` с вариантами **`Move`, `Say`, `Quit`, `Tick`**. Меняются порядок вариантов, структура текста `MyString`, способ обхода массива, извлечение логики в `score`, подсказка `#[inline(always)]`, попытка использовать `chunks_exact`, настройки/варианты программ и сравнения через `hyperfine`. В кадрах видны также ошибки компиляции при попытке передать некопируемое событие по значению: это важный сигнал, что сначала нужно соблюдать владение и контракты.

Наблюдения, **не универсальные гарантии**:

1. Положение `Tick` в объявлении `enum` может сопутствовать изменению машинного кода. Причины следует искать в дискриминанте, layout, коде `match`, расположении переходов, профиле ветвей и оптимизациях LLVM; «первым всегда хуже» или «последним всегда лучше» — неверные правила.
2. Замена выделяемой строки `String` на встроенный массив байтов меняет размер события, число аллокаций и **поддерживаемые входы**. Фиксированный буфер на 15 байтов не заменяет произвольный UTF-8 `String` без политики переполнения.
3. Вынесенная функция `score(&Event)` и `#[inline(always)]` могут менять кодогенерацию, однако инлайнинг иногда увеличивает бинарник и нагрузку на I-cache.
4. Обработка фиксированными блоками (`chunks_exact(4)`) предлагает компилятору понятную структуру, но остаётся обязательным правильно обработать хвост. Ручная раскрутка цикла без доказательства преимуществ не является оптимизацией.
5. Числа в демонстрационном `hyperfine` принадлежат конкретным бинарникам и машине из ролика (на экране виден macOS arm64); не стоит считать их скоростью вашего x86-64 Haswell.

### 24.3. Очень важное правило интерпретации роликов

**Факт из видео:** авторы перебирают формы исходного кода и сравнивают конкретные бинарники. **Инженерная гипотеза:** какой именно участок сгенерированного машинного кода объясняет результат. **Нужное доказательство:** одинаковые входы/результат, версия компилятора и флаги, `size_of`, disassembly, `perf stat` или эквивалентные счётчики, повторные замеры. Удачный пример в ролике — повод поставить собственный эксперимент, а не шаблон для слепого применения.

## 25. Как Rust превращает текст в быстрый или медленный машинный код

### 25.1. Мысленная схема компиляции

```text
Код Rust (.rs)
   ↓ разбор, типизация, проверка владения / заимствований
HIR → MIR (контроль потока, места хранения, drop, проверки)
   ↓ MIR-оптимизации, мономорфизация дженериков
LLVM IR (SSA, ветви, load/store, векторные операции)
   ↓ LLVM: inlining, GVN, LICM, SROA, vectorization, instruction selection
Ассемблер → object files → линковка / LTO
   ↓
Машинный код в ELF → CPU: ветви, кэш, TLB, порты, декодеры, спекуляция
```

Это приближённая схема: точные стадии и их порядок зависят от версии компилятора. **MIR и LLVM IR не являются байт-кодом виртуальной машины:** обычная Rust-программа Linux/x86-64 исполняет нативные инструкции. «Посмотреть байт-код» для этого случая обычно значит посмотреть MIR, LLVM IR и дизассемблированный ELF.

### 25.2. Компилятору помогает не магический синтаксис, а информация

| Что должно быть ясно оптимизатору | Как выразить в Rust | Возможный эффект | В каких случаях не сработает |
|---|---|---|---|
| Границы индексов | `for item in &slice`, `zip`, `chunks_exact`, заранее ограниченный срез | Устранение части bounds checks | Сложная индексация, несовпадение длин |
| Длина массива известна | `[T; N]`, `chunks_exact(N)`, константный размер блока | Развёртывание, специализация | Большой N раздувает код |
| Нет нужды в копировании | `&T`, `&str`, `&[u8]`, `Cow` по контракту | Меньше аллокаций и копий | Владение должно пережить источник |
| Нужен лишь top K | отбор до клонирования, heap / selection | Меньше работы | K близко к N, стабильность порядка |
| Инвариант не меняется | вычислить один раз перед циклом | LICM/сокращение вызовов | Вычисление имеет побочные эффекты |
| Нужен ровно один проход | `fold`, потоковая обработка | Меньше временных коллекций | Нарушается порядок ошибок/эффектов |
| Все элементы независимы | последовательный проход по `&mut [T]` | Автовекторизация | Зависимости между итерациями |
| Ветка чрезвычайно редка | разнести hot/cold пути | Лучший layout и I-cache | Распределение ветвей меняется |
| Тип вызова статический | дженерик вместо `dyn Trait` | Возможность инлайнинга | code bloat, больше сборка |
| Платформа известна | `target-cpu`, условный SIMD | Использование ISA | Бинарник не переносим |

Изменения *типов*, *контрактов* и *структуры данных* обычно сильнее влияют на оптимизацию, чем перестановка пробелов или имён переменных. Однако каждый из перечисленных эффектов требует проверки.

### 25.3. Модель затрат: чего искать в горячем цикле

На каждой итерации оценивайте количество:

- инструкций, зависимых одна от другой (critical path);
- случайных чтений памяти и промахов кэша;
- предсказуемых и непредсказуемых ветвлений;
- аллокаций, освобождений, увеличений capacity;
- вызовов, которые не удалось встроить;
- проверок границ, динамических диспетчеризаций, делений;
- операций синхронизации (lock, atomic, fence);
- вызовов системных функций (`read`, `write`, `clock_gettime` и т. д.).

Не всё из этого дорого всегда: условная инструкция может быть дешевле создания маски, а аллокация вне горячего пути может вообще не иметь значения.

## 26. Переписывание Rust для более понятного оптимизатору кода: 25 приёмов

### C01. Итерация по элементам вместо повторного индексирования

```rust
fn indexed(data: &[u64]) -> u64 {
    let mut total = 0u64;
    for i in 0..data.len() {
        total = total.wrapping_add(data[i]);
    }
    total
}

fn iterated(data: &[u64]) -> u64 {
    data.iter().copied().fold(0u64, u64::wrapping_add)
}
```

Современный LLVM часто одинаково оптимизирует оба варианта. `wrapping_add` выбран для тождественной семантики во всех профилях. Смотрите, остались ли проверки границ в машинном коде, и не делайте выводов только по виду Rust-кода.

### C02. Ограничить срез *перед* многократным индексированием

```rust
fn add_prefix(data: &[u32], count: usize) -> Option<u64> {
    let prefix = data.get(..count)?;
    let mut sum = 0u64;
    for &value in prefix {
        sum += u64::from(value);
    }
    Some(sum)
}
```

Проверка границы происходит при получении среза; основной проход по элементам не требует ручных `get_unchecked`. Если раньше функция паниковала при неверном `count`, возврат `Option` **меняет контракт**: используйте в сравнении варианты с одинаковой реакцией на ошибки.

### C03. `zip` — когда по контракту допустимо обрезать до кратчайшего входа

```rust
fn dot_min_length(left: &[u32], right: &[u32]) -> u64 {
    left.iter().zip(right).map(|(&a, &b)| u64::from(a) * u64::from(b)).sum()
}
```

`zip` прекращает итерацию при исчерпании *любого* входа. Если требуется совпадение длин, сначала отдельно проверяйте длины; нельзя «ускорять», молча теряя хвост.

### C04. `chunks_exact` — когда блоки полные и хвост не забыт

```rust
fn sum_four(data: &[u32]) -> u64 {
    let mut blocks = data.chunks_exact(4);
    let mut total = 0u64;
    for block in blocks.by_ref() {
        total += u64::from(block[0]) + u64::from(block[1]);
        total += u64::from(block[2]) + u64::from(block[3]);
    }
    for &value in blocks.remainder() {
        total += u64::from(value);
    }
    total
}
```

Проверяйте длины `0..=7`, нечётные размеры и большие массивы. Блоки могут помочь развёртыванию, но компилятор нередко уже выполняет его самостоятельно.

### C05. Вынос инварианта из цикла без изменения побочных эффектов

```rust
fn scale(data: &mut [u32], base: u32) {
    let factor = base.wrapping_mul(17).wrapping_add(3);
    for value in data {
        *value = value.wrapping_mul(factor);
    }
}
```

Ручной вынос полезен, когда LLVM не может доказать, что вызов чистый, или не видит определение. Вызов логгера, чтение времени либо lock нельзя просто вынести: изменится поведение.

### C06. Удалять временные `Vec`, но не менять порядок вычислений

```rust
fn positive_sum(data: &[i32]) -> i64 {
    data.iter().filter(|&&value| value > 0).map(|&value| i64::from(value)).sum()
}
```

Вместо цепочки `filter(...).collect::<Vec<_>>()` → `iter().sum()` можно выполнить один проход. Если промежуточная коллекция используется дальше, её удаление уже неэквивалентно.

### C07. Собирать только то, что нужно на выходе

Выбор между `filter(...).cloned().collect()` и `filter(...).collect::<Vec<&T>>()` зависит от стоимости клона и числа отброшенных позднее объектов. Не возвращайте ссылки на локальный `Vec`/временный объект. См. раздел 24.1.

### C08. Сначала отфильтровать, затем дорого вычислять

```rust
fn total_length(lines: &[String]) -> usize {
    lines.iter().filter(|line| line.starts_with('X')).map(String::len).sum()
}
```

Иногда перестановка `map` и `filter` корректна, но **не всегда**: может измениться число вызовов функций, порядок ошибок, паник или побочных эффектов.

### C09. Упростить зависимость между итерациями

```rust
fn two_sums(data: &[u64]) -> (u64, u64) {
    let mut even = 0u64;
    let mut odd = 0u64;
    for (index, &value) in data.iter().enumerate() {
        if index & 1 == 0 {
            even = even.wrapping_add(value);
        } else {
            odd = odd.wrapping_add(value);
        }
    }
    (even, odd)
}
```

Несколько независимых накопителей могут сокращать цепочку зависимостей. Иногда рост давления на регистры и ветвлений делает код хуже. Для `float` перегруппировка сложений может изменить точные биты результата.

### C10. Ранний `return` для редкой ошибки — только без пропуска очистки

```rust
fn first_nonzero(data: &[u32]) -> Option<u32> {
    data.iter().copied().find(|value| *value != 0)
}
```

Ранний выход сокращает работы при подходящем распределении входов. Если первоначальный код всегда проходил весь массив ради телеметрии или побочных эффектов, это уже изменение поведения.

### C11. Холодный путь `#[cold]`

```rust
#[cold]
fn report_unexpected(value: u32) -> String {
    format!("unexpected value: {value}")
}

fn check(value: u32) -> Result<u32, String> {
    if value <= 1000 { Ok(value) } else { Err(report_unexpected(value)) }
}
```

`#[cold]` — подсказка компилятору; она не делает редкую ветку бесплатной, а выделение `String` остаётся на пути ошибки. При частых ошибках такая подсказка способна ухудшать расположение кода.

### C12. `#[inline]`, `#[inline(always)]`, `#[inline(never)]` — локальные эксперименты

Инлайнинг устраняет границу вызова и открывает оптимизатору тело функции, но увеличивает размер кода. Сравните бинарный размер, I-cache и `perf annotate`; **принудительный inline не всегда быстрее обычного вызова**. Не навешивайте атрибут на все функции проекта.

### C13. Разделить тяжёлый `enum` на горячие и холодные данные

Если почти все события — небольшие `Tick` и `Move`, а редкий `Say` содержит текст, возможны два варианта: хранить события с ссылками/индексами на отдельное текстовое хранилище либо разнести потоки событий по типам. Выигрыш возможен за счёт меньшего `size_of::<Event>()` и плотного чтения, но **порядок событий и время жизни данных** нужно сохранить явно.

### C14. Заменить `String` фиксированным буфером только с чётким ограничением

```rust
struct AsciiWord {
    len: u8,
    bytes: [u8; 15],
}

impl AsciiWord {
    fn new(input: &str) -> Option<Self> {
        if input.len() > 15 || !input.is_ascii() { return None; }
        let mut bytes = [0; 15];
        bytes[..input.len()].copy_from_slice(input.as_bytes());
        Some(Self { len: input.len() as u8, bytes })
    }

    fn as_str(&self) -> &str {
        // Записанные байты проверены как ASCII, значит они являются UTF-8.
        std::str::from_utf8(&self.bytes[..usize::from(self.len)]).unwrap_or("")
    }
}
```

Это **не** прозрачная замена произвольного `String`: теперь вход может быть отвергнут. Внешняя зависимость для SmallString не обязательна, но написание собственного безопасного контейнера добавляет код и тесты.

### C15. Вводить `with_capacity` только при реальной предсказуемости размера

`Vec::with_capacity(estimate)` снижает возможные realloc, но большое завышение расходует RSS и кэш. Для коротких событий при переменном размере иногда выгоднее обычный `Vec::new()`.

### C16. Повторно использовать буфер

После обработки партии `buffer.clear()` сохраняет capacity, но вызывает `Drop` элементов. Для буфера `Vec<u8>` стоимость очистки обычно невелика; для сложного `Vec<T>` могут быть дорогими деструкторы.

### C17. Выбирать `Vec` против `HashMap` по реальной операции

Поиск в `Vec` линейный, но память последовательна и ветвлений мало; маленькая таблица может проигрывать `HashMap`. При уникальном ID и плотном диапазоне индексов прямой `Vec<Option<T>>` иногда радикально дешевле хеша, но требует ограничения диапазона и управления памятью.

### C18. Вместо `contains_key` + `insert` использовать `entry`

Два поиска в таблице часто избыточны. Использование `entry` меняет форму кода, но не обязательно улучшает время на маленьких таблицах. Учитывайте, что вычисление значения по умолчанию через `or_insert` происходит заранее; `or_insert_with` ленивый.

### C19. Отделять разбор чисел от форматирования

Не конвертируйте числа в `String`, чтобы снова распарсить их в `u64`. Но замена `parse::<u64>()` собственным циклом по байтам обязана точно сохранить правила знака, пустого ввода, переполнения и пробелов.

### C20. Уменьшать динамическую диспетчеризацию в внутреннем цикле

`fn process<T: Trait>(data: &[T])` помогает мономорфизации и инлайнингу по сравнению с `&dyn Trait`. Цена: больше экземпляров машинного кода и большая сборка. Если узкое место вне вызова, выгоды может не быть.

### C21. Принудительно не распараллеливать мелкие задачи

Создание потоков и координация стоят времени. Прежде чем делить 1–1000 элементов, измерьте одноядерную реализацию и порог, где параллельность окупается. Внутренний цикл без границ задач часто выигрывает от последовательного выполнения.

### C22. `std::hint::black_box` — только для измерения

`black_box` не ускоряет бизнес-код: он специально мешает некоторым оптимизациям убирать вычисления в тестах. Это best-effort механизм, не барьер памяти и не инструмент корректности.

### C23. Битовая маска вместо `HashSet` — только для небольшого ограниченного диапазона

```rust
fn has_flag(mask: u64, flag: u32) -> bool {
    flag < 64 && (mask & (1u64 << flag)) != 0
}
```

При `flag >= 64` нужна отдельная логика, иначе возможны паники или другое поведение при сдвиге. Маска лишает вас произвольных ключей и требует определения битового протокола.

### C24. `sort_unstable` против `sort` — осознанная смена контракта

Нестабильная сортировка может использовать меньше памяти и выигрывать на ваших данных, но порядок равных ключей может измениться. Если порядок событий с равным временем важен, сохраняйте дополнительный порядковый номер или стабильную сортировку.

### C25. Не переписывать всё на `unsafe`

Только если `perf` показывает остаточные bounds checks или другой доказанный ущерб, рассмотрите низкоуровневый подход. Подтверждение инвариантов должно покрывать **все входы**, включая пустой срез, короткий хвост, переполнение длины и aliasing. Бенчмарки не доказывают безопасность `unsafe`.


## 27. События, `Tick`, порядок вариантов `enum`: почему перестановка строк иногда вызывает регресс

### 27.1. Различайте четыре разных порядка

1. **Порядок объявления вариантов:** `enum Event { Tick, Move, Say }` против `{ Move, Say, Tick }`. Он может менять дискриминанты, layout и машинный код, но не гарантирует направление ускорения.
2. **Порядок веток `match`:** ветвь `Tick =>` сверху или снизу. Rust-компилятор может преобразовать обе формы к одинаковому `switch`/таблице переходов или по-разному расположить базовые блоки. Вид исходника не является порядком реальных проверок CPU.
3. **Порядок событий в данных:** `[Tick, Move, Tick, ...]` против `[Move, Move, Tick, ...]`. Этот порядок влияет на предсказание ветвлений, локальность и **семантику игры/сервера**. Его нельзя переставлять без доказательства коммутативности действий.
4. **Порядок обработки в цикле:** `for event in log` против группировки по типам/батчам. Сортировка событий ради производительности может нарушить временную причинность, порядок сообщений, воспроизводимость и fairness.

Если «`Tick` сверху» замедлил программу, сначала запишите **какой из четырёх порядков был изменён**. Это самый важный диагностический вопрос.

### 27.2. Точный эксперимент с типами событий

```rust
#[derive(Clone)]
enum TickFirst {
    Tick,
    Move { id: u32, dx: i16, dy: i16 },
    Say { id: u32, text: String },
    Quit { id: u32, code: u8 },
}

#[derive(Clone)]
enum TickLast {
    Move { id: u32, dx: i16, dy: i16 },
    Say { id: u32, text: String },
    Quit { id: u32, code: u8 },
    Tick,
}

fn inspect_layout() {
    println!("first: {}", std::mem::size_of::<TickFirst>());
    println!("last: {}", std::mem::size_of::<TickLast>());
    println!("align(first): {}", std::mem::align_of::<TickFirst>());
    println!("align(last): {}", std::mem::align_of::<TickLast>());
}
```

Два `enum` — два разных типа, их размер и layout не обязаны совпадать (хотя могут совпасть). При построении честного теста создайте *одинаковую последовательность логических событий*; результаты должны быть идентичны. Меняйте только объявление `enum`, а не одновременно тип строки, число проходов, компилятор и порядок данных. `size_of` также **не показывает** размер heap-буферов, на которые ссылается `String`.

### 27.3. `#[repr(u8)]` — не переключатель «сделай быстрее»

Для простого перечисления с явным протоколом:

```rust
#[repr(u8)]
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
enum EventKind {
    Tick = 0,
    Move = 1,
    Say = 2,
    Quit = 3,
}
```

Здесь численные дискриминанты явно заданы. Но `#[repr(u8)]` на сложном `enum` с payload может менять представление и оптимизации; нельзя делать вывод, что весь объект будет размером **один байт**. Если формат по сети/диску должен быть стабильным, задавайте явную сериализацию: тег + длина + payload с однозначным endian, а не `transmute` памяти `enum`.

**Протокол эксперимента:** `repr(Rust)` → замер; поменять только порядок вариантов → замер; `repr(u8)` → замер отдельно; сравнить `size_of`, число аллокаций, `perf stat`, hot assembly и семантику. `std::mem::discriminant()` годится для сравнения вариантов в рамках программы, но не как числовой идентификатор в сети.

### 27.4. Иногда дело не в варианте `Tick`, а в размере КАЖДОГО события

```text
Vec<Event> хранит элементы с одинаковым stride = size_of::<Event>()
            ┌────────────┬────────────┬────────────┐
            │ Event #0   │ Event #1   │ Event #2   │ ...
            └────────────┴────────────┴────────────┘

Если Say содержит большой inline-payload, даже Tick может занимать
в массиве столько же места, сколько самый крупный вариант + tag/padding.
```

При миллионах событий увеличение `size_of::<Event>()` на несколько байтов может изменить число cache lines, размер рабочего набора и число промахов. Перенос текста в отдельное хранилище может уменьшить stride, но добавляет указатель/индекс и второй доступ к памяти. Сравните `Vec<Event>`, `Vec<Box<Event>>` и структуру hot/cold: **`Box` не гарантирует выигрыш**, потому что ухудшает локальность и добавляет аллокации.

### 27.5. Частый `Tick` и редкие события: раздельные hot/cold обработчики

```rust
struct World {
    ticks: u64,
    total_dx: i64,
}

enum Event {
    Tick,
    Move { dx: i16 },
    Error { message: String },
}

#[cold]
fn process_error(message: &str) {
    eprintln!("event error: {message}");
}

fn process_event(world: &mut World, event: &Event) {
    match event {
        Event::Tick => world.ticks = world.ticks.wrapping_add(1),
        Event::Move { dx } => world.total_dx += i64::from(*dx),
        Event::Error { message } => process_error(message),
    }
}
```

В этом примере `Error` действительно должен быть редким, иначе `#[cold]` может навредить. `eprintln!` — лишь пример обработки ошибки, не подходящий для latency-critical пути. Если сообщения должны быть обработаны в строго определённой очередности, не выносите ошибки в конец кадра автоматически.

### 27.6. Tick «каждый кадр» против Tick «на каждое событие»

Уточните бизнес-семантику: `Tick` — это одно продвижение состояния мира, маркер времени, условие flush, heartbeat или произвольное событие в очереди? Это **разные задачи**.

- **Плохой случай:** при 100 000 входящих сообщениях каждый handler вызывает обновление *всего* мира. Это `O(events × entities)` вместо возможного `O(events + ticks × entities)`.
- **Возможный дизайн:** один запланированный fixed-step tick обновляет мир, а обработчики сообщений только добавляют изменения/команды в очередь. Нужно определить, в какой момент применяются команды, и не ломать детерминизм.
- **Опасная «оптимизация»:** объединить несколько тиков в один `world.ticks += count`. Если между тиками изменяются таймеры, физика, collisions или callback-и — это неэквивалентно.
- **Плохая идея:** каждый раз читать `Instant::now()` внутри внутреннего цикла событий, если одно значение времени на batch достаточно по контракту.
- **Ещё одна плохая идея:** заменить фиксированный timestep величиной `elapsed` без анализа интегратора и численной устойчивости.

### 27.7. Предсказание ветвей: сгенерируйте четыре формы распределения

Для теста `match` используйте одни и те же события, но разные *корректные* статистики нагрузки: (A) 99% `Tick`; (B) все варианты равновероятны; (C) длинные серии одинаковых вариантов; (D) случайное перемешивание с фиксированным seed. Порядок вариантов в `enum` меняйте независимо от распределения входов. Смотрите `branches`, `branch-misses` и инструкции, но помните: эти счётчики не объясняют всё (может быть bottleneck в памяти, а не branch predictor).

### 27.8. Защита семантики при рефакторинге event loop

Проверьте: порядок `Tick` относительно `Move/Say/Quit`, результат для пустой очереди, точную кратность ticks, `Quit` как терминальное событие, reentrancy обработчиков, исключения/паники, время life-cycle объектов, overflow счётчиков, backpressure и лимит обработки событий за кадр. Используйте replay одного event log до и после; сравнивайте полный snapshot мира, а не только один `total`.

### 27.9. Матрица вариантов эксперимента

| Независимая переменная | Значения | Что держим постоянным |
|---|---|---|
| Расположение `Tick` | первым / последним / середина | событие и payload те же |
| Тип текста | `String` / отдельное хранилище / inline с лимитом | контракт входов или явная фильтрация |
| Вычисление score | `match` в цикле / функция / инлайнинг | точный результат |
| Проход | `iter()` / `chunks_exact(4)` с хвостом | число событий и порядок |
| Данные | hot tick / uniform / shuffled / burst | seed, N, PASS |
| Машина | portable x86-64 / Haswell-specific | сравнивать только внутри каждой платформы |

**Вывод:** «Перенеси `Tick` вверх/вниз» — не правило. Правило: *выясни семантику, размеры типов, порядок нагрузки, наблюдаемый assembly и метрики; затем проверь перестановку как изолированный эксперимент*.

## 28. Искусство измерения: почему `Instant` и `Tick` в неправильном месте портят результат

### 28.1. Что именно надо измерять

- **Время одного вызова** — для горячего микрофункционала; полезно только при достаточно длинном прогоне и защите от выкидывания работы компилятором.
- **Throughput** — сколько событий/секунда, с учётом очередей и реального I/O.
- **Latency p50/p95/p99** — длительность отдельной операции, в том числе на редких медленных входах.
- **Рабочий набор** — RSS, выделенные байты и число аллокаций, cache misses.
- **Время одного тика** — полная работа цикла кадра, а не стоимость одного `match`.

### 28.2. Плохой benchmark: clock на каждой итерации

```rust
use std::time::Instant;

fn bad_timing(events: &[u64]) -> u128 {
    let mut total_ns = 0u128;
    for &value in events {
        let started = Instant::now(); // Измеряем и стоимость чтения часов.
        std::hint::black_box(value.wrapping_mul(3));
        total_ns += started.elapsed().as_nanos();
    }
    total_ns
}
```

Это меряет не только обработчик, но и два обращения к таймеру на элемент; в очень коротком обработчике инструментирование может доминировать. Кроме того, компилятор может иначе оптимизировать код, когда в него вставлены дополнительные вызовы и зависимости.

### 28.3. Лучше: мерить целую партию

```rust
use std::hint::black_box;
use std::time::{Duration, Instant};

fn process_batch(events: &[u64]) -> u64 {
    events.iter().copied().fold(0u64, |sum, value| {
        sum.wrapping_add(value.wrapping_mul(3))
    })
}

fn time_batch(events: &[u64], rounds: usize) -> Duration {
    let started = Instant::now();
    let mut checksum = 0u64;
    for _ in 0..rounds {
        checksum ^= black_box(process_batch(black_box(events)));
    }
    black_box(checksum);
    started.elapsed()
}
```

Здесь `black_box` находится **на границе** `process_batch`, а не внутри горячего цикла, чтобы не препятствовать оптимизации исследуемых операций. `black_box` — best effort; эквивалентность результата проверяйте отдельным тестом. Проверьте также, что исходная реальная функция действительно делает требуемую работу и вход/выход контролируются компилятором.

### 28.4. ABBA — минимальная дисциплина сравнения

```text
Warmup: A, B несколько раз (не включать в отчёт)
Block 1: A → B → B → A
Block 2: B → A → A → B  (или рандомизация блоков с сохранением баланса)
...
Block 15+: чередовать блоки; хранить сырые измерения
```

Меняйте вариант только после того, как проверили одинаковую работу и сборку. Сохраняйте параметры `rustc -Vv`, температуру/частоты CPU при возможности, governor, `taskset`, фоновую нагрузку, объём данных и **все измерения**, а не один лучший результат. На перегруженной машине или при thermal throttling вывод может быть некорректен.

### 28.5. Почему иногда «ускорилось» только от перестановки строк

Факторы: изменился layout инструкций, выравнивание функций/ветвей, icache, поведение branch predictor, расположение данных, результаты PGO, размер бинарника, порядок линковки, уровень оптимизации, turboboost и просто шум. Порой небольшая перестановка текста меняет хэш LLVM, порядок генерации кода либо решения эвристик. Нужны **повторения с разными последовательностями сборки** и подтверждение в disassembly.

### 28.6. На какой точке ставить таймер при реальном game/event tick

```text
frame begin
  ├─ drain input queue         [отдельный таймер, по желанию]
  ├─ process queued events     [отдельный таймер, по желанию]
  ├─ fixed-step world tick     [отдельный таймер, по желанию]
  ├─ render / network flush    [отдельный таймер, по желанию]
frame end ← ВАЖНА полная длительность кадра
```

Старайтесь делать статистику **выборочной** (например, один кадр из N) или агрегировать числовые счётчики на более редком пути. Логирование каждой операции меняет производительность особенно сильно. Для профилирования используйте семплирование CPU, а не печать на каждое событие.

### 28.7. Не путать wall time, user CPU time и cycles

Программа может ждать сеть/диск и иметь высокую задержку при низкой загрузке CPU. `perf stat` полезен для CPU-bound кода, `strace -c` — для чрезмерных syscall (влияние `strace` на время существенно), `iostat`/`pidstat` и обычная телеметрия — для I/O. Суммарное CPU time многопоточного приложения может превышать wall time.

## 29. Как смотреть MIR, LLVM IR и настоящие машинные инструкции

### 29.1. Полезные команды без nightly

```bash
# Сначала фиксируем конфигурацию инструментария и целевой процессор.
rustc -Vv
rustc --print target-cpus | grep -E 'haswell|native|generic' || true

# Пример из отдельного файла example.rs, только std, без зависимостей:
rustc --edition=2021 -C opt-level=3 --crate-type=lib \
  --emit=mir,llvm-ir,asm example.rs
# Обычно получатся example.mir, example.ll, example.s.

# Для Cargo-проекта (укажите свой bin):
cargo rustc --release --bin my_program -- --emit=asm
# Сгенерированный .s ищите в target/release/deps/.

# Бинарник с line tables и frame pointers для perf.
# Внимание: debuginfo=1 сам код не меняет, а force-frame-pointers=yes МЕНЯЕТ
# кодогенерацию (резервирует регистр, добавляет пролог/эпилог, влияет на
# register pressure и иногда на инлайнинг). Это profiling-сборка, а не
# shipping-сборка: абсолютные числа с неё нельзя переносить на релиз.
RUSTFLAGS='-C debuginfo=1 -C force-frame-pointers=yes' cargo build --release

# Дизассемблирование уже слинкованного ELF:
objdump -d -C --no-show-raw-insn target/release/my_program > executable.asm
# Альтернатива при установленном LLVM:
llvm-objdump -d --demangle target/release/my_program > executable-llvm.asm
```

`rustc --emit=mir` — стабильная опция вывода, **но внутренний формат MIR не является стабильным API**; различия между версиями Rust нормально ожидаемы. Генерация `.s` не равна дизассемблированию готового ELF: линковка/LTO и расположение функций могут изменить итоговую картину.

### 29.2. Что смотреть на каждом уровне

| Слой | Признак | Что значит | Что делать |
|---|---|---|---|
| MIR | лишний `Clone` или временная коллекция | создание/копирование данных | сравнить исходный алгоритм |
| MIR | branches, asserts, cleanup/drop | потенциальные проверки и управление потоком | проверить, что не исчезают после LLVM |
| LLVM IR | `load`, `store`, `alloca`, `getelementptr` | работа с памятью, промежуточный SSA | искать лишние memory ops, но `alloca` в IR не обязательно heap/stack в финальном коде |
| LLVM IR | `llvm.memcpy`, `llvm.memmove` | перенос данных | проверить объём и частоту |
| LLVM IR | `call` vs `inlined` | вызов сохранён или встроен | поискать вызов в финальном assembly |
| LLVM IR | vector types `<4 x i64>` | потенциальная SIMD-операция | проверить конечные x86 инструкции |
| Assembly | `call` to alloc / dealloc | аллокатор в горячем участке | уменьшить количество выделений |
| Assembly | `cmp` + `jcc` | условное ветвление | увидеть, часто ли mispredict |
| Assembly | `div` / `idiv` | аппаратное целочисленное деление | проверить, можно ли поменять алгоритм/операнды |
| Assembly | `vmov*`, `vpadd*` | векторные операции на поддерживаемом ISA | проверить с реальным CPU и tail path |
| Perf | cache misses / stalled cycles | возможная memory-bound работа | менять layout/доступы, а не арифметику |

Наличие `call`, `cmp` или `load` **само по себе не доказательство проблемы**. Важно, сколько времени/циклов они занимают в настоящем горячем участке.

### 29.3. Как найти функцию внутри огромного ELF

```bash
nm -C target/release/my_program | grep -E 'score|process_event|recent_orders'
objdump -d -C target/release/my_program | less
# Профиль полезнее случайного просмотра всех функций:
perf record -g -- ./target/release/my_program
perf report
perf annotate --stdio
```

Для узких функций, которые полностью инлайнились, отдельного символа может не быть. Смотрите *вызывающую* функцию и line-level attribution. Для сравнения машинного кода используйте `diff -u before.s after.s`, а лучше два слинкованных бинарника с одинаковыми flags.

### 29.4. `cargo-asm`, Compiler Explorer и другие инструменты

`cargo-asm` — сторонний инструмент для просмотра assembly функций из Cargo-проекта; нужен отдельный `cargo install` и совместимость с версией Rust. `https://godbolt.org/` (Compiler Explorer) позволяет сравнивать исходник и asm **онлайн**, но не отправляйте туда приватный/секретный код. В отличие от веб-сервиса, локальные команды выше не требуют публикации исходников.

### 29.5. Где искать именно проблему bounds checks

В дизассемблере смотрите холодные вызовы panic/bounds-check пути и сравнения длины с индексом. Сначала попробуйте безопасную форму `for value in slice`, предобрезанный срез, `chunks_exact`, доказанный `assert!` инвариант. Только если реальный горячий цикл всё ещё страдает и профили это показывают, можно обсуждать `unsafe get_unchecked` с формальным доказательством границ.

### 29.6. Если компилятор полностью удалил вашу «работу»

```rust
fn main() {
    let mut sum = 0u64;
    for i in 0..1_000_000u64 {
        sum = sum.wrapping_add(i);
    }
    // Даже println! может позволить компилятору заменить цикл формулой.
    println!("{sum}");
}
```

Оптимизатор имеет право вычислить константный результат заранее: это **хорошая оптимизация** реального кода, но плохая основа для микробенчмарка цикла. Передавайте runtime-данные извне и проверяйте, что тест измеряет искомую операцию, а не константное выражение/артефакт `black_box`.


## 30. Чтение ассемблера x86-64: какие инструкции реально стоят времени

Это **словарь для чтения**, а не гарантия конкретного количества тактов. Латентность и пропускная способность инструкций зависят от микроархитектуры, операндов, зависимостей, выравнивания, кэша, частот и соседних инструкций.

### 30.1. Мини-словарь типичных инструкций

| Группа | Примеры | Что обычно делает | Что проверять |
|---|---|---|---|
| Загрузка/сохранение | `mov`, `vmovdqu`, `vmovdqa` | перенос регистров/памяти | адреса, размер, промахи cache/TLB |
| Арифметика | `add`, `sub`, `imul` | сложение, вычитание, умножение | overflow, зависимости, ширина |
| Деление | `div`, `idiv` | частное и остаток | частота, можно ли изменить задачу |
| Битовые операции | `and`, `or`, `xor`, `shl`, `shr`, `sar` | маски, сдвиги | ограничение диапазона, знаковость |
| Адресная арифметика | `lea` | вычислить линейную комбинацию адресных компонентов | часто просто эффективная целочисленная арифметика |
| Сравнение | `cmp`, `test` | установить flags | следующий `jcc` / `setcc` / `cmov` |
| Переходы | `jmp`, `je`, `jne`, `ja`, `jl` | условный/безусловный переход | предсказуемость, плотность кода |
| Выбор без перехода | `cmovcc`, `setcc` | условный выбор/байт из flags | цепочка зависимостей и стоимость обеих веток |
| Вызовы | `call`, `ret` | переход к функции и обратно | остались ли вызовы внутри горячего цикла |
| Стек | `push`, `pop`, `sub rsp` | сохранение регистров/кадр | spills, стековые буферы |
| Атомарность | `lock add`, `lock cmpxchg`, `xchg` | синхронизация между ядрами | contention, cache-line bouncing |
| SIMD integer | `vpaddd`, `vpaddq`, `vpcmpeqb`, `vpshufb` | параллельная обработка элементов | ширина регистров, ISA и хвост |
| SIMD float | `vaddps`, `vmulps`, `vfmadd*` | операции над `f32` / FMA | округление, точность, NaN, reassociation |
| Векторный переход ISA | `vzeroupper` | избегание части AVX/SSE penalty | важен на некоторых поколениях x86 |
| Системный вызов | `syscall` | переход в ядро | batching, буферизация, количество calls |

**Не делайте вывод:** «в asm есть 100 инструкций, значит оно медленнее, чем 80». У CPU out-of-order execution, speculation и микрооперации; критична стоимость *зависимой цепочки* и bottleneck ресурсов.

### 30.2. Режимы адресации и `lea`

Общая форма x86-64 адресации: `[base + index*scale + displacement]`, где `scale` обычно 1/2/4/8. Поэтому доступ к элементу `u64` часто обходится без отдельного умножения индекса на 8. `lea rax, [rdi + rsi*4]` может означать арифметическое `a + 4*b`, а не загрузку памяти; само название инструкции вводит в заблуждение.

### 30.3. Ветвление или `cmov`: не существует универсального победителя

```rust
fn min_branch(left: i32, right: i32) -> i32 {
    if left < right { left } else { right }
}
```

LLVM может породить conditional move, инструкцию `min` либо branch в зависимости от контекста и CPU. `cmov` не имеет misprediction, но создаёт зависимость и вычисляет оба значения выбора до назначения; для дорогой ветки нельзя всегда заменить `if` на «безветвленную» арифметику. На распределении 99% одного исхода предсказуемый branch может быть лучше.

### 30.4. Инструкции с памятью — часто важнее чистой арифметики

```text
A: последовательное чтение 16 KiB из L1D    → возможно CPU-bound (если эти данные действительно находятся в L1D)
B: случайное чтение большого массива         → часто latency/memory-bound
C: запись в один атомик из 16 потоков         → часто contention-bound
D: memcpy больших непрерывных фрагментов      → bandwidth-bound
```

Это **возможные режимы**, а не измеренные здесь характеристики. Например, L1D у Intel Haswell составляет 32 KiB на ядро: массив в 64 KiB не поместится в нём целиком. Проверяйте `perf stat` и профиль памяти. Замена `i * 8` на `i << 3` ничего не даёт, если главное — промахи LLC.

### 30.5. Разворот цикла (`unroll`) и независимые аккумуляторы

```rust
fn sum_u64(data: &[u64]) -> u64 {
    let mut a = 0u64;
    let mut b = 0u64;
    for pair in data.chunks_exact(2) {
        a = a.wrapping_add(pair[0]);
        b = b.wrapping_add(pair[1]);
    }
    let tail = data.len() & 1;
    if tail != 0 {
        a = a.wrapping_add(data[data.len() - 1]);
    }
    a.wrapping_add(b)
}
```

Две цепочки `add` потенциально позволяют использовать параллелизм инструкций. Проверяйте массивы длины 0, 1, 2, 3 и чётные/нечётные крупные. Выбор `wrapping` обеспечивает одинаковую арифметику по модулю 2^64; рефакторинг `f64` так делать без допуска погрешности нельзя.

### 30.6. Когда «пропал» диапазон проверок

Если безопасный код проверяет `data[i]`, rustc может оставить ветку `i < len` и холодный panic path, а может доказать, что условие всегда истинно. Сравните `cargo rustc --release -- --emit=asm` и `perf annotate`; главное — **число исполнений**, а не присутствие текстового символа panic в любом месте бинарника.

### 30.7. Intel Haswell: на что смотреть именно на Xeon E5-2680 v3

- Есть AVX2 и FMA, **нет AVX-512**. Бинарник с AVX-512 не предназначен для этой машины.
- Регистры YMM 256 бит; это не значит, что любой цикл автоматически получит 4×/8× ускорение.
- Для локальной сборки под данную модель сравните `-C target-cpu=haswell`, `-C target-cpu=native` и portable baseline. Названия допустимых CPU проверяйте через `rustc --print target-cpus`.
- Смотрите взаимодействие AVX2 с частотой/нагревом, памятью и размером входа; результаты другой архитектуры, в частности macOS ARM64 из видео, не переносимы напрямую.
- Полезно отдельно измерить 1 поток, 12 физических ядер и 24 логических потока: hyper-threading может помогать или мешать в зависимости от нагрузки.

### 30.8. `llvm-mca`: оценка пропускной способности asm, а не профилировщик программы

```bash
# Требуется установленный LLVM с llvm-mca и подготовленный asm-фрагмент.
llvm-mca -mcpu=haswell hot_loop.s
```

Анализатор использует модель планировщика инструкций для конкретного CPU и помогает найти давление на порты и длинные цепочки зависимостей. Он **не** учитывает полноценно реальное попадание данных в кэш, поведение ОС, все виды ветвлений и другие внешние факторы. Принимать решение следует по `perf` и wall-time на целевой машине.

### 30.9. Как выглядит нормальный разбор одного горячего цикла

1. Функция занимает, допустим, 40% CPU samples — **это гипотетический пример**, не число вашего кода.
2. В `perf annotate` 60% семплов внутри цикла приходятся на `idiv`, `load` или переходы.
3. Сопоставьте строку Rust с инструкцией, проверьте частоту исполнения и входные данные.
4. Сформулируйте гипотезу: заменить общий хеш-контейнер на плотный индекс либо устранить повторное деление.
5. Проверьте эквивалентность и сравните raw ABBA на тех же данных.
6. Проверьте, исчезло ли узкое место, и нет ли регрессии в другом участке.

## 31. `perf` от нуля до объяснения регрессии

### 31.1. Диагностика доступа

```bash
perf --version
perf list | less
cat /proc/sys/kernel/perf_event_paranoid
uname -r
```

Если `perf` пишет «not permitted», проверьте настройки ядра, политику вашей машины/контейнера и права администратора; не советуется бездумно отключать защиту системы. Контейнеру могут быть недоступны PMU hardware events.

### 31.2. Базовая диагностика CPU

```bash
# Семь повторов: время, инструкции, циклы, ветвления, промахи и cache misses.
perf stat -r 7 -e cycles,instructions,branches,branch-misses,cache-references,cache-misses \
  -- ./target/release/my_program input.bin

# Подробные метрики (набор счётчиков зависит от CPU/ядра):
perf stat -d -- ./target/release/my_program input.bin

# Сэмплирование с call graph:
perf record -F 99 -g -- ./target/release/my_program input.bin
perf report --stdio
perf annotate --stdio
```

`perf stat` обычно пишет результат в **stderr**. Не путайте `cache-misses` со строго «L1 data misses»: символическое событие может обозначать другой уровень/условие; проверьте определение на конкретном CPU. Если `perf` multiplex-ит слишком много событий, счётчики могут быть масштабированы и менее точны: сначала берите небольшой набор событий.

### 31.3. Какие выводы из счётчиков допустимы

| Наблюдение | Возможная причина | Что проверить сначала |
|---|---|---|
| Много cycles, мало instructions | ожидание данных / зависимые операции | LLC, dTLB, sampling addresses |
| Высокий branch-miss rate | случайный `match`, непредсказуемые условия | распределение типов событий |
| Много instructions и низкий branch miss | лишняя логика/форматирование | число проходов и temporary allocations |
| Много cache misses | плохая локальность, pointer chasing | SoA, packing, batch size |
| Значительная sys CPU time | частые syscall, locks, page faults | I/O batching, contention |
| Низкая загрузка CPU, высокий wall time | ожидание сети/диска/очереди | latency traces, `pidstat`, async wakeups |
| Рост p99, стабильная средняя | GC чужого компонента, lock, sched, I/O, page faults | трассировка хвоста и корреляция |

Выводы **неоднозначны**. Высокий branch-miss rate может не означать значительную стоимость, если ветвлений мало. Низкий IPC не всегда плох: нагрузка может быть ограничена пропускной способностью памяти по своей природе.

### 31.4. IPC, CPI и цена ошибок предсказания

Для синхронно собранных аппаратных счётчиков:

- `IPC = instructions / cycles`;
- `CPI = cycles / instructions`;
- `miss-rate = branch-misses / branches`.

Не сравнивайте IPC между произвольными программами как «рейтинг качества». Одно широкое SIMD-вычисление может делать много полезной работы при небольшом числе инструкций; другие инструкции могут быть микро-кодированы или иметь несколько μops. Реальное время — первичная цель.

### 31.5. Сравнение двух сборок

```bash
# Сначала убедитесь, что сравниваются два существующих бинарника.
perf stat -r 7 -- ./before input.bin
perf stat -r 7 -- ./after input.bin

# Затем общий протокол ABBA на одинаковых входах и в одном окружении.
# Сохраните sha256sum before after, rustc -Vv, RUSTFLAGS и отчёт.
sha256sum ./before ./after
```

Если всё различие объясняется только одной необычной сборкой, повторите сборку обеих версий **в чистом target directory** для контроля флагов. Результаты PGO и layout после линковки могут менять вывод.

## 32. Математика производительности: оптимизации, которые можно обосновать формулами

### 32.1. Закон Амдала: предел ускорения

Если доля времени горячей части до оптимизации равна `p`, а саму часть удалось ускорить в `s` раз, полное ускорение ограничено:

```text
S_total = 1 / ((1 − p) + p / s)
```

**Пример:** если оптимизируемая часть занимала 50% времени и стала в 10 раз быстрее, весь процесс ускорится только приблизительно в **1,82 раза**. Если в результате узким местом становится I/O, новое оптимизирование того же цикла уже мало помогает.

### 32.2. Roofline: ограничение вычислениями или пропускной способностью памяти

```text
Арифметическая интенсивность I = полезные операции / считанные+записанные байты
Производительность ≤ min(пиковая вычислительная скорость, пропускная способность памяти × I)
```

Эта модель особенно полезна для больших массивов, матриц и SIMD. Ускорять арифметику бессмысленно, если данные уже упёрлись в bandwidth. Наоборот, если рабочий набор помещается в L1 и bottleneck в зависимом `div`, оптимизация памяти может не помочь.

### 32.3. Приведение сложности алгоритма к реальному порогу

```text
T_linear(n) ≈ c1·n
T_hash(n) ≈ c2·hash_cost + c3·random_memory_access
T_sort(n) ≈ c4·n·log2(n)
T_binary_search(n) ≈ c5·log2(n)·random_access_cost
```

Константы неизвестны без измерения. Малый `Vec` может обходить `HashMap` из-за непрерывных чтений, несмотря на худшую асимптотику для больших `n`. Для часто читаемой неизменной таблицы отсортированный `Vec` + binary search может быть выгоднее карты, но обновление данных становится дороже.

### 32.4. Уменьшение числа операций важнее «быстрой инструкции»

```rust
// Исходный алгоритм: n раз заново суммируем префикс — O(n²).
fn prefix_quadratic(data: &[u32]) -> Vec<u64> {
    (0..data.len()).map(|i| {
        data[..=i].iter().map(|&v| u64::from(v)).sum()
    }).collect()
}

// Кандидат: одно сканирование — O(n).
fn prefix_linear(data: &[u32]) -> Vec<u64> {
    let mut total = 0u64;
    let mut result = Vec::with_capacity(data.len());
    for &value in data {
        total += u64::from(value);
        result.push(total);
    }
    result
}
```

Числа должны помещаться в `u64`, иначе исходные результаты также зависят от переполнения: для полной эквивалентности при произвольных размерах используйте `wrapping_add` в обеих версиях или возвращайте проверяемую ошибку при overflow.

### 32.5. Дешёвое вычисление остатка: когда битовая маска корректна

Для беззнакового числа `x` и `m = 2^k > 0`:

```text
x % m == x & (m - 1)
```

Но `x % 10` **не равно** `x & 9`, а для знаковых отрицательных чисел перенос формулы требует другого доказательства. Если `m` — константа, LLVM уже часто оптимизирует `% m` в умножение на «магическую» константу и сдвиг. Ручные замены без профиля нередко избыточны.

### 32.6. Умножение, деление и сдвиги

- `x * 8` для unsigned обычно уже оптимизируется в сдвиг/адресную арифметику, если это выгодно.
- `x / 8` для unsigned похоже на `x >> 3`; для signed отрицательных деление с усечением к нулю не тождественно арифметическому сдвигу.
- `wrapping_mul` и `checked_mul` имеют разные контракты, даже когда профили дают похожий asm.
- Сдвиг на величину `>=` ширины типа недопустимо превращать в «как-нибудь замаскируем shift» без явного решения по семантике.

### 32.7. Числа с плавающей точкой — отдельная дисциплина

Перестановка `a + b + c` в `a + (b + c)` может изменить округление, переполнение, NaN и signed zero. Сведение нескольких сумм в одну SIMD-редукцию может изменить биты результата. FMA (`a*b + c` одной операцией) может быть точнее, но не побитово совпадать с отдельным умножением и сложением. Определите tolerance: абсолютную/относительную/ULP, режим обработки NaN, инфинити и `-0.0`; затем тестируйте на значениях рядом с границами.

### 32.8. Численная устойчивость важнее максимальной SIMD-ширины

- Для многих сумм `f32` может экономить память, но давать плохую точность.
- Попарная сумма и алгоритм Кэхэна уменьшают ошибку на некоторых входах, но требуют операций.
- Для статистики используйте устойчивые алгоритмы, например Welford, вместо `E[x²] − E[x]²` без оценки потери точности.
- Для геометрии/физики используйте ограничения диапазона, тесты на денормалы и near-zero; не включайте агрессивные floating-point трансформации без явного допуска.

### 32.9. Выигрыш от параллелизма и его порог окупаемости

```text
T_parallel ≈ T_work / P_eff + T_split + T_schedule + T_merge + T_contention
```

При малом `T_work` накладные расходы превосходят полезную работу. `P_eff` зависит от ресурсов ядра, синхронизации, памяти, SMT и реальной распараллеливаемости. Большее число потоков не равно лучшей производительности. Для серверов важен также p99, а не только throughput.

### 32.10. Полезная работа на один байт

Математическое сокращение данных часто сильнее низкоуровневых трюков:

- хранить индексы `u32` вместо `usize` **только если диапазон гарантирован**;
- обрабатывать координаты как SoA, если задача часто читает только `x`;
- использовать сжатые битовые множества для плотных small-int ID;
- избегать дублирующихся `String` через интернирование только при контролируемом жизненном цикле;
- обрабатывать матрицы блоками, если они не помещаются в кэш.

**Не оптимизируйте арифметику там, где выигрыш может дать уменьшение числа прочитанных cache lines.**


## 33. Архитектурные приёмы: локальность, aliasing, SIMD, многопоточность

### 33.1. Array of Structures (AoS) и Structure of Arrays (SoA)

```rust
struct Entity {
    x: f32,
    y: f32,
    health: u16,
    active: bool,
}

struct EntitySoA {
    x: Vec<f32>,
    y: Vec<f32>,
    health: Vec<u16>,
    active: Vec<bool>,
}
```

Если каждый кадр меняются только `x/y`, SoA потенциально позволяет читать меньше ненужных байтов и эффективнее векторизовать проход. Если почти каждая операция читает все поля одного `Entity`, AoS может быть лучше. Для SoA **все длины векторов должны быть согласованы**, а удаление элемента требует одновременного обновления всех колонок. `Vec<bool>` **не упаковывает значения по битам**: `bool` занимает один байт. Для упакованных флагов можно применить маску или `bitvec`, учитывая накладные расходы на декодирование. [std::mem::size_of](https://doc.rust-lang.org/std/mem/fn.size_of.html), [bool](https://doc.rust-lang.org/std/primitive.bool.html).

### 33.2. False sharing: независимые счётчики могут мешать друг другу

```rust
use std::sync::atomic::{AtomicU64, Ordering};

#[repr(align(64))]
struct PaddedCounter(AtomicU64);

impl PaddedCounter {
    fn increment(&self) {
        self.0.fetch_add(1, Ordering::Relaxed);
    }
}
```

При обновлении разных слов в **одной cache line** ядра могут часто передавать владение линией друг другу. Выравнивание на 64 байта — характерная гипотеза для ряда x86, но размер линий и эффект надо проверять на CPU; увеличивается расход памяти, а `repr(align(64))` не гарантирует полезного размещения всех объектов в каждом allocator/container. `Relaxed` здесь подходит лишь для независимого счётчика; для публикации данных другим потокам нужен другой протокол синхронизации.

### 33.3. Runtime SIMD dispatch без AVX-512

```rust
#[cfg(target_arch = "x86_64")]
fn supports_avx2() -> bool {
    std::arch::is_x86_feature_detected!("avx2")
}

#[cfg(not(target_arch = "x86_64"))]
fn supports_avx2() -> bool { false }
```

Функцию с AVX2 intrinsics следует пометить соответствующим `#[target_feature(enable = "avx2")]`, а переход в неё выполнять **только после CPU feature check**; опасные вызовы находятся в `unsafe` и нуждаются в комментарии `SAFETY` с доказательством. Для любых целевых CPU без AVX2 оставляйте безопасную scalar fallback реализацию. Если весь бинарник собран под `-C target-cpu=haswell`, он уже не обязан запускаться на старых x86-64.

### 33.4. Batching и справедливость

Объединение 100 событий в batch может снижать overhead channel/lock/syscall, но увеличивать ожидание редких событий и p99. Сохраняйте ограничения fairness, порядок для одного клиента, дедлайны, управление отменой и реакции на `Quit`. Разный batch size тестируйте на пиковых и редких нагрузках, не только на среднем throughput.

## 34. Как отличать истинный выигрыш компилятора от повреждения смысла

### 34.1. Семь классов контрактов, которые легко сломать

1. **Порядок:** стабильная сортировка, порядок событий, FIFO, tie-breakers.
2. **Количество:** `zip` обрезает, `chunks_exact` оставляет remainder, `.take(limit)` меняет количество обработанных элементов.
3. **Числа:** `checked` vs `wrapping`, signed shifts, `usize` vs `u32`, float NaN и rounding.
4. **Строки:** UTF-8 и Unicode; slicing по байтам может попадать между символами.
5. **Ошибки:** panic vs `Option` vs `Result`, момент обнаружения ошибки, частичные side effects.
6. **Конкурентность:** memory order, потеря/дублирование сообщений, race condition, состояние `Mutex` после panic.
7. **Наблюдаемые эффекты:** логи, метрики, счётчики, `Drop`, время вызова внешнего API.

### 34.2. Два разных класса отрицательных примеров

- **Медленнее, но корректно:** лишний `clone`, неоправданный `HashMap`, чрезмерное распараллеливание. Нужен бенчмарк, чтобы назвать конкретный пример медленнее.
- **Неверно по семантике:** потеря хвоста, изменение порядка с нарушением контракта, неверное переполнение. Нужен тест-контрпример, чтобы доказать несовпадение результата.

Не смешивайте эти классы в одной метке `slower`: ошибочный результат может достигаться очень быстро, но это не оптимизация.


Полный список конкретных семантических ловушек приведён в §20: здесь важна **проверка классификации**, а не повтор таблицы.

## 35. Гайд для нейросети: как оптимизировать чужой Rust-проект профессионально

### 35.1. Роль AI

AI — помощник инженера по производительности. Её цель: **сформулировать воспроизводимую гипотезу, предложить минимальный patch, доказать сохранение контракта и измерить на целевой системе**. Если доступа к исходникам/компилятору/bench нет, AI должна чётко сказать, чего не знает; не выдумывать ускорение или результаты тестов.

### 35.2. Готовая инструкция для системного/первого сообщения AI

Скопируйте этот блок в системные инструкции нейросети вместе с проектом:

> **ЗАДАЧА:** оптимизируй Rust-программу, сохранив её заявленное поведение. Не оптимизируй ради красивого исходника и не меняй API, стабильность сортировки, порядок событий, panic/error контракт, точность float или многопоточную семантику без отдельного обоснования и теста.
>
> **ПОРЯДОК:** (1) установи целевую нагрузку и платформу; (2) изучи код, тесты, Cargo profile и зависимости; (3) собери/запусти baseline, если инструменты доступны; (4) по профилю найди горячее место; (5) предложи до трёх идей с оценкой рисков и проверяемой гипотезой; (6) применяй по одной минимальной правке; (7) проверь тесты, крайние случаи, release, измерения и машинный код; (8) оставляй только подтверждённые улучшения. Если нет возможности запустить код — не утверждай, что тесты прошли или что стало быстрее.
>
> **ПРОИЗВОДИТЕЛЬНОСТЬ:** ищи сначала асимптотику, лишнюю работу и аллокации, потом layout/cache/branching, затем инструкции и флаги. Не начинай с `unsafe`, SIMD, `#[inline(always)]`, изменения `enum` или ручной branchless-арифметики.
>
> **СОБЫТИЯ:** различай порядок вариантов enum, порядок ветвей match, порядок событий в логе и порядок обработки; проверь частоту Tick, размеры payload и replay детерминированного event log. Не переставляй Tick только потому, что так было быстрее в чужом видео.
>
> **МАШИННЫЙ КОД:** при наличии инструментария сопоставь MIR/LLVM IR/ELF disassembly и `perf` с конкретным hot loop. Не называй отдельную инструкцию причиной регрессии без подтверждения её стоимости и частоты исполнения.
>
> **ПРОВЕРКА:** тесты на пустые/маленькие/огромные входы, одинаковые ключи, переполнение, UTF-8, разные частоты событий, параллельность и 100% воспроизводимый seed. ABBA-бенчмарк release; сырые результаты; версия rustc, CPU, flags. Если ускорение меньше шума, пометь `unknown`.
>
 **ВЫХОД:** короткий диагноз; контракт; 1–3 гипотезы с оценкой риска; патч; тесты; команды компиляции/профилирования; результаты (реальные или «не выполнялось»); решение `keep/revert/unknown`; потенциальные регрессии.

### 35.3. Шаблон задачи, которую человек передаёт AI

```text
Цель: снизить [latency p99 / throughput / memory / binary size].
Платформа: [CPU, OS, rustc -Vv, core count, RAM].
Команда сборки: [точный cargo command + RUSTFLAGS].
Команда запуска: [точный command, input files, seed].
Контракт: [порядок событий, overflow, ошибки, Unicode, float tolerance].
Текущий профиль: [perf stat/record/flamegraph/raw measurements].
Место оптимизации: [module::function, исходник].
Нельзя менять: [публичное API, output, serialization, deterministic replay].
Можно использовать dependencies/unsafe? [да/нет + пределы].
Нужно: [минимальный diff, тесты, методика проверки, объяснение ASM].
```

### 35.4. Обязательная структура ответа AI

```text
DIAGNOSIS
- Что конкретно горячее и чем подтверждается?
- CPU-bound / memory-bound / contention / I/O / unknown?

SEMANTIC CONTRACT
- Что должно остаться точно тем же?
- Какие ошибочные входы и побочные эффекты учтены?

HYPOTHESIS
- Какая операция будет удалена (alloc, copy, hash, branch, load)?
- Что ожидается на уровне MIR / LLVM / asm?
- На каких N/распределениях может проиграть?

PATCH
- Минимальный diff (не десятки несвязанных исправлений).
- Без unsafe, кроме отдельно обоснованного исключения.

CORRECTNESS
- Тесты до/после + эталонный oracle при возможности.
- Конкретные edge cases; изменения контракта объявлены.

BENCHMARK
- Команда сборки, входы, warmup, ABBA, сырые времена.
- Median/dispersion; метрики cycles/instructions/cache-misses.
- Если запуск невозможен: "not measured" без вымышленных цифр.

ASSEMBLY
- Чем реально отличаются hot blocks.
- Если disassembly недоступен: явно "not inspected".

DECISION
- keep/revert/unknown и причина.
```

### 35.5. Протокол оценки предложений AI

| Критерий | Высокое качество | Низкое качество |
|---|---|---|
| Корректность | тесты и контракт сохранены | изменены порядок/погрешность/ошибки без пометки |
| Локализация | найден hot spot | «оптимизировал всё подряд» |
| Измерения | воспроизводимый release ABBA | «быстрее на глаз» |
| Ясность | есть гипотеза про операции/кэш | только «LLVM это любит» |
| Риски | описаны негативные сценарии | не учтены маленькие N, Unicode, ошибки |
| Машинный код | связан с профильными samples | механический подсчёт инструкций |
| Сопровождение | минимальный читаемый diff | unsafe/макросы/спецхак без необходимости |

### 35.6. AI должна спрашивать не «что оптимизировать?», а «где теряется время?»

Если пользователь прислал только функцию, возможен анализ сложности, аллокаций и контрактов, но не подтверждение runtime-выигрыша. Если есть полный проект, начните со сборки и профиля. Если предоставлено видео с чужим ускорением, используйте его как гипотезу, а не как измерения для данного проекта.

### 35.7. Сопоставление Rust-кода с `perf annotate`: формат объяснения AI

```text
src/events.rs:process_events() → 37% CPU samples [гипотетическое число]
Область: match Event + обработка payload
Assembly: load discriminant → conditional branches → load String payload
Counters: branch-misses ↑, LLC misses ↑ [нужно проверить реально]
Гипотеза: payload редкого Say увеличивает stride всех событий.
Кандидат: изменить layout только после проверки size_of и lifetime.
Тест: deterministic event log; сравнить полный state и событие Quit.
Решение: unknown до фактического профиля и release-бенчмарка.
```

Пример выше **иллюстрирует формат отчёта**. Ни 37%, ни рост счётчиков не относятся к вашему коду и не измерялись здесь.

### 35.8. Нейросеть не должна вносить опасные изменения, маскируя их под оптимизацию

Отдельное подтверждение требуется для: замены арифметики `checked → wrapping`, работы с указателями, FFI/ABI/layout, `unsafe`, атомарного ordering, отказа от tail processing, исключения событий из лога, изменения тайминга tick, перестановки событий, укорочения payload, переключения sort stable/unstable и агрессивного SIMD с иной точностью.


## 36. Практикум для тебя: от одной функции до понимания, почему она медленная

### 36.1. Создай отдельный учебный файл

Сохрани `sample.rs`:

```rust
#[inline(never)]
#[unsafe(no_mangle)]
pub fn count_above(values: &[u32], threshold: u32) -> usize {
    values.iter().filter(|&&value| value > threshold).count()
}

#[inline(never)]
#[unsafe(no_mangle)]
pub fn count_above_index(values: &[u32], threshold: u32) -> usize {
    let mut count = 0usize;
    for i in 0..values.len() {
        if values[i] > threshold {
            count += 1;
        }
    }
    count
}
```

Символы экспортированы, чтобы компилятор оставил две функции, которые можно сравнить в asm. `#[unsafe(no_mangle)]` нужен для явно контролируемого имени символа; в настоящем API без необходимости не используйте no_mangle (в том числе из-за риска конфликта символов). Эти две функции эквивалентны по обычной семантике `usize` для тех же срезов.

### 36.2. Собери и сравни на Haswell

```bash
mkdir -p out
rustc --edition=2024 --crate-type=lib -C opt-level=3 -C target-cpu=haswell \
  --emit=asm,llvm-ir,mir --out-dir out sample.rs

ls -lh out/
grep -n 'count_above' out/*.s
# Открой и изучи код вокруг обеих меток функций.
less out/*.s
```

Это **статический эксперимент**; на самом Haswell для оценки скорости понадобится отдельный исполняемый бенчмарк, вызывающий обе функции с одинаковыми runtime-входами. Не делай вывод «iterators быстрее индексов» только по одному `.s`: вполне возможно, что LLVM создал одинаковые петли.

### 36.3. Как интерпретировать возможную разницу

- Одинаковая форма в asm → на данном уровне, скорее всего, различия исходника незначимы для функции; проверь binary и бенчмарк.
- Есть дополнительный `cmp + jae` + panic target → возможно, осталась проверка границ; проверь, действительно ли она исполняется на каждом элементе.
- Есть `vpcmpeqd` или другой векторный цикл → LLVM использовал SIMD для какого-то участка; проверь ISA и tail path.
- Различается длина тела → не равно различию времени: нужные данные даст `perf`.

### 36.4. Получение собственного baseline для настоящего Cargo-проекта

```bash
# 1. Проверка корректности и конфигурации.
rustc -Vv
cargo test --locked
cargo clippy --all-targets --all-features -- -W clippy::perf

# 2. Release с line tables и frame pointers.
RUSTFLAGS='-C debuginfo=1 -C force-frame-pointers=yes' cargo build --release --locked

# 3. Несколько повторов, нормальная рабочая нагрузка.
perf stat -r 7 -- ./target/release/my_program realistic_input.dat

# 4. Горячие участки + call graph.
perf record -g -- ./target/release/my_program realistic_input.dat
perf report
perf annotate --stdio
```

`cargo test --locked` фиксирует разрешённые зависимости, но само по себе не доказывает полной идентичности среды. Избегай проверки только `cargo test` без проверок поведения на больших входах; тесты и профили нужны оба. С включением debuginfo release остаётся оптимизированным, но расположение секций и результат линковки могут немного измениться — для очень точных исследований сравнивай одинаковые debug flags в A и B.

### 36.5. Что делать, если `perf` недоступен

1. Начни с `time`, `/usr/bin/time -v`, собственного бенчмарка с `Instant` *вокруг партии*.
2. Профилируй выделения памяти (инструмент по доступности), посмотри их источники.
3. Сгенерируй `.s` через `cargo rustc`, посмотри `objdump`/`llvm-objdump`.
4. Для полноценного аппаратного профиля используй Linux host, где разрешён PMU.
5. Если тестируешь на другом процессоре, записывай, что результаты **не целевые**.

### 36.6. Упрощённый порядок ревью любого замедления

```text
Программа стала медленнее?
  ├─ Ошибка корректности или изменён контракт? → откатить, починить тест
  ├─ Разные флаги / сборки / входные данные? → исправить эксперимент
  ├─ Статистически неотличимо от шума? → unknown, больше повторов
  ├─ Выросли allocations / RSS? → проверить клоны, буферы, layout
  ├─ Выросли cache misses? → память, stride, указатели, hot/cold
  ├─ Выросли branch misses? → распределение event, match, dispatch
  ├─ Выросли инструкции / CPU? → повторная работа, деление, сортировки
  ├─ Вырос sys time? → syscall, locks, I/O
  └─ Нет объяснения? → снять более подробный профиль, не угадывать
```


## 37. Экспертная сборка: PGO без дублирования базовых флагов

Настройки LTO, CGU, `target-cpu`, размеры кода и правила безопасности описаны в §§3, 14, 18 и 20. Здесь оставлен **пошаговый PGO-workflow**; повторять общие советы не нужно.

### 37.1. PGO: компилятор узнаёт реальную частоту веток

```bash
# Порядок приведён как схема; замените target и my_program для вашего проекта.
TARGET=x86_64-unknown-linux-gnu
PGO_DIR="$(pwd)/pgo-data"
mkdir -p "$PGO_DIR"

RUSTFLAGS="-Cprofile-generate=$PGO_DIR" \
  cargo build --release --target "$TARGET"

./target/$TARGET/release/my_program representative_input_1.dat
./target/$TARGET/release/my_program representative_input_2.dat

# llvm-profdata ищите в llvm-tools компонентах или установленном LLVM:
llvm-profdata merge -o "$PGO_DIR/merged.profdata" "$PGO_DIR"/*.profraw

RUSTFLAGS="-Cprofile-use=$PGO_DIR/merged.profdata" \
  cargo build --release --target "$TARGET"
```

**Внимание:** профиль должен отражать реальное распределение событий (`Tick/Move/Say/Quit`) и размеры входов. Иначе оптимизатор улучшит не ту ветку. В некоторых сборках rustc/инструментации имена profraw содержат идентификаторы и файлов может быть несколько; пути, версии LLVM и режим сборки сверяйте с [официальным PGO workflow](https://doc.rust-lang.org/rustc/profile-guided-optimization.html). При повторных экспериментах чистите старые `.profraw`, чтобы не смешивать профили разных программ.

| `assert_matches!`, `debug_assert_matches!` | 1.96.0 | Более информативные проверки pattern-инвариантов | Для тестирования, не ускорение само по себе |
| Новый формат Rust symbol mangling v0 по умолчанию | 1.97.0 | Сопоставление имён с ASM и профилем | Символы могут отличаться от старых сборок; обновляйте анализаторы |
| `CARGO_BUILD_WARNINGS=deny` | 1.97.0 | Строгие предупреждения CI без изменения флагов `rustc` | Другой механизм, чем глобальное `RUSTFLAGS=-Dwarnings` |
| `<integer>::format_into(&mut NumBuffer<T>)` | 1.98.0 | Форматирование десятичных целых в переиспользуемый буфер | Время жизни выданного `&str` связано с буфером; сравнивайте с `write!` |
| `str::substr_range`, `[T]::subslice_range` | 1.98.0 | Узнать диапазон подсреза относительно исходного объекта | Не заменяют проверку допустимости среза и инвариантов lifetime |
| `f32/f64::algebraic_add/sub/mul/div/rem` | 1.98.0 | Дать LLVM право на алгебраические преобразования float | **[В]** допускают иной порядок, округление, обработку особых значений; не выбирать для точных/воспроизводимых вычислений |
| `Vec::into_parts`, `Vec::from_parts`; `Box::into_non_null` | 1.99.0 | Сложные FFI, allocator/ownership-пайплайны | `unsafe` и сохранение layout, capacity, provenance, allocator инвариантов; не нужны обычным приложениям |
| `String::from_utf8_lossy_owned` | 1.99.0 | Конвертировать *владеющий* байтовый буфер с заменой некорректного UTF-8 | Lossy-конверсия **меняет содержимое** на невалидном UTF-8 |
| Новый встроенный профиль Cargo `debug` | 1.99.0 | Подготовка к будущему разделению профилей `dev`/`debug` | На 1.99 пока эквивалентен `dev`; не считать отдельной оптимизацией |
| Cargo отключает incremental по умолчанию при `CI` | 1.99.0 | Лучше понимать времена сборок в CI | Сравнивайте с одинаковыми переменными среды и `CARGO_INCREMENTAL` |

Основные источники: [1.95](https://blog.rust-lang.org/2026/04/16/Rust-1.95.0/), [1.96](https://blog.rust-lang.org/2026/05/28/Rust-1.96.0/), [1.97](https://blog.rust-lang.org/2026/07/09/Rust-1.97.0/), [1.98](https://blog.rust-lang.org/2026/08/20/Rust-1.98.0/), [1.99](https://blog.rust-lang.org/2026/10/01/Rust-1.99.0/), [Cargo changelog](https://doc.rust-lang.org/cargo/CHANGELOG.html).

### 39.2. Пример: изменять только что вставленный элемент (stable 1.95+)

```rust
fn build_labels(ids: &[u32]) -> Vec<String> {
    let mut labels = Vec::with_capacity(ids.len());
    for id in ids {
        let label: &mut String = labels.push_mut(String::new());
        label.push_str("id=");
        label.push_str(&id.to_string());
    }
    labels
}

#[test]
fn stable_push_mut_keeps_order() {
    assert_eq!(build_labels(&[3, 9]), ["id=3", "id=9"]);
}
```

Это *пример нового API*, **не benchmark**. Здесь всё ещё создаётся временный `String` при `id.to_string()`. В действительно горячем пути нужно сравнить `write!`, `format_into` и исходный вариант с реальными входами. Функционально схожий старый вариант — `labels.push(String::new()); labels.last_mut().unwrap().push_str(...)`; лишняя индексация не обязана приводить к дополнительным машинным инструкциям.

### 39.3. Пример: `as_chunks` и обязательный хвост (stable 1.88+)

```rust
fn sum_pairs(xs: &[u32]) -> u64 {
    let (pairs, remainder) = xs.as_chunks::<2>();
    let mut acc = 0_u64;
    for &[a, b] in pairs {
        acc += u64::from(a) + u64::from(b);
    }
    for &x in remainder {
        acc += u64::from(x);
    }
    acc
}

#[test]
fn never_loses_tail() {
    assert_eq!(sum_pairs(&[]), 0);
    assert_eq!(sum_pairs(&[1]), 1);
    assert_eq!(sum_pairs(&[1, 2, 3]), 6);
}
```

Здесь сумма вычисляется в `u64`, но в общем случае достаточно большой вход и большие элементы могут переполнить `u64` — правила ошибок/переполнения должны быть частью контракта. Этот небольшой пример демонстрирует полноту обработки, а не автоматическое ускорение.

### 39.4. Что нельзя переносить из «нового stable» в каждый проект

- Нельзя использовать API из 1.95/1.98/1.99 при требуемом MSRV 1.88. В библиотеке записывайте `rust-version` в `Cargo.toml`, держите отдельную проверку MSRV и документируйте альтернативный код.
- Не меняйте арифметику `f64` на `algebraic_*` при требовании битового совпадения результата: возможны различия между CPU, компиляторами и флагами. Для численных алгоритмов формализуйте tolerance/NaN/Infinity и тестируйте также отрицательный ноль.
- Версия toolchain важна даже без изменения исходника: LLVM, стандартная библиотека и линкер могут производить другой машинный код, а в 1.99.1 исправлены регрессии 1.99.0 (включая неверную кодогенерацию FFI `bool` на x86-64). [Патч-ноты 1.99.1](https://blog.rust-lang.org/releases/latest/).

## 40. Будущие версии: beta 1.100, nightly и контролируемый watchlist

### 40.1. Классы достоверности

**Три разных утверждения, которые нельзя смешивать:**

1. **[STABLE]** подтверждено релизом и стабильной документацией конкретной версии — можно рекомендовать с указанием MSRV.
2. **[BETA-PLANNED]** есть в beta или черновике релиза, но финальная дата/API могут измениться; **не считать stable до официального анонса**.
3. **[NIGHTLY/PROPOSAL]** есть экспериментальный флаг, tracking issue, RFC или PR; **нет гарантированной даты** стабилизации. Наличие PR ≠ merge, merge ≠ стабилизация, стабилизация на master ≠ доступность на stable.

### 40.2. Что действительно содержится в черновике Rust 1.100

Проверка на **2026-11-09** по официальному [черновику release notes rust-lang/rust #163811](https://github.com/rust-lang/rust/issues/163811). Ниже именно **план 1.100**, а не факт уже состоявшегося релиза.

| Возможность [BETA-PLANNED] | Значение для производительности | Что перепроверить 12.11.2026 |
|---|---|---|
| `Allocator`, `Global`, `System`, `Vec::new_in/with_capacity_in`, `Box::new_in` | Пер-объектный выбор аллокатора, потенциально более точное управление arena/пулами | Стабилизирован ли полный нужный набор API и какие ограничения allocator type |
| `-C profile-sample-use` | Путь к sample-based PGO для платформ/рабочих процессов, где подходят профили семплирования | Поддерживаемый формат профиля, версии LLVM, target, режим компиляции |
| Изменения Cargo build-dir layout v2 | Влияние на кэш/скрипты CI и инструменты, просматривающие `target/` | Не полагаться на внутренний каталог; получать артефакты через `--message-format=json` |
| Стабилизация never type `!` | Семантика типов и поведение type inference; косвенно — dead-code анализ | Совместимость библиотеки, компиляция тестов и зависимостей |
| `Box::take`, `Box::map`, `Rc::map`, `Arc::map` | Перемещение/преобразование владения с сохранением корректного смысла | Сигнатуры, ограничения, реальное поведение при ошибках/паникующих closure |
| `bool::toggle` | Удобная модификация флага, **не оптимизация сама по себе** | Наличие в окончательном stable релизе |

**Пример для beta 1.100, НЕ stable 1.99:**

```rust
// Только для beta 1.100, если API действительно стабилизирован
// в установленной beta. Не вставлять в основной stable-проект.
use std::alloc::System;

fn make_buffer() -> Vec<u8, System> {
    let mut v = Vec::with_capacity_in(128, System);
    v.extend_from_slice(b"abc");
    v
}
```

Проверка без смены глобальной версии: `rustup toolchain install beta` → `cargo +beta check` в **отдельном экспериментальном crate**. `System` не обязан быть быстрее глобального аллокатора. Пользовательский arena-аллокатор может снижать число системных вызовов в конкретной схеме выделений, но может удерживать память, менять lifetime-ограничения, ухудшать RSS и latency. Старые программы на stable продолжают использовать глобальный аллокатор и `Vec::with_capacity`.

**Sample PGO:** в отличие от instrumentation PGO из §37, sample profile получают профилировщиком. Не используйте вымышленную команду конвертации формата: сначала прочтите [rustc PGO guide](https://doc.rust-lang.org/rustc/profile-guided-optimization.html), release notes своего `rustc` и документацию генератора sample profile. Параметр `-C profile-sample-use` из черновика **не гарантирован** на stable 1.99.

**Cargo 1.100:** draft changelog прямо предупреждает, что меняется внутренняя структура промежуточных файлов сборки. Не пишите скрипт вида `find target/debug/deps/...` с предположением о неизменном layout. Для имени и пути собранного артефакта используйте сообщения Cargo. [Cargo beta changelog](https://doc.rust-lang.org/beta/cargo/CHANGELOG.html).

```rust
#![feature(portable_simd)]
use std::simd::Simd;

fn add_four(a: [u32; 4], b: [u32; 4]) -> [u32; 4] {
    (Simd::from_array(a) + Simd::from_array(b)).to_array()
}

fn main() {

}
```

Запускать только `rustc +nightly` в изолированном тестовом проекте. Пример не измерен; производительность зависит от target и машинного кода. **Не включайте nightly-only возможности в основной stable-поток без явного согласия на nightly.**

### 40.4. Автоматический способ не устаревать: дисциплина проверки перед обновлением

```bash
# Обновлять каналы раздельно; не менять глобальный default ради теста:
rustup toolchain install stable beta nightly
rustc +stable -Vv
rustc +beta -Vv
rustc +nightly -Vv

# Из корня СВОЕГО проекта:
cargo +stable test --all-targets
cargo +beta test --all-targets
cargo +nightly check --all-targets

# Для каждой кандидата по сборке и скорости нужна отдельная release-матрица:
cargo +stable build --release
cargo +beta build --release
```

- `rustup toolchain install` требует сети, команды `+beta/+nightly` могут скачивать обновления, установленная beta иногда недоступна для выбранного target.
- **Тестовый код beta** держите в отдельном crate/CI-job; если `#![feature(...)]` не существует или функция изменена, не придумывайте совместимость.
- **Каждые шесть недель** после публикации stable: обновить версии в таблице, посмотреть релиз и Cargo changelog, перенести подтверждённое из `BETA-PLANNED` в `STABLE`, изменить MSRV только если согласовано, запустить тестовую матрицу и производственные benchmarks. ## 41. Проверка корректности: Miri, fuzzing, property-based и конкурентность

### 41.1. Пирамида доказательств для оптимизации

| Уровень | Какой класс ошибок обнаруживает | Чего НЕ доказывает |
|---|---|---|
| `cargo test` + golden/reference fixtures | Явное изменение результата и порядка на тестовых входах | Все возможные входы и все interleavings |
| Property-based: `proptest` | Большие классы входов + минимальный counterexample | Полное математическое доказательство |
| Differential fuzzing: `cargo-fuzz` | Расхождение референсной и новой реализации, crashes | Отсутствие ошибок за пределами достигнутых путей |
| Miri | Многие виды UB: aliasing, некорректное чтение памяти, некоторая гонка данных | Скорость, полнота поддержки ОС/FFI, все UB |
| Loom | Интерливинги моделируемых `loom::sync` примитивов на маленьких состояниях | Ошибки вне модели, произвольные внешние I/O, все interleavings больших систем |
| Sanitizers (ASan/TSan/UBSan по возможности) | Часть memory errors / гонок на нативном коде | Семантическую эквивалентность и абсолютную безопасность |
| Release-сборка + production replay | Детерминизм, настоящие ошибки компилятора/линковки и интеграции | Все возможные нагрузки, все процессоры |

**Правило:** `unsafe` требует явного safety contract, но даже полностью safe-патч может быть неверен из-за пропуска элементов, изменения порядка сообщений, overflow и float rounding. Результаты тестов — это свидетельства, а не доказательство универсальной эквивалентности.

### 41.2. Конкретный differential/property тест

Для пары функций `select_active_before/after` из приложенного учебного проекта можно добавить отдельный файл `tests/properties.rs`:

```rust
// [dev-dependencies] proptest = "1"; версию запишите в Cargo.lock.
use proptest::prelude::*;
use rust_perf_case::{select_active_before, select_active_after};

proptest! {
    #[test]
    fn order_and_duplicates_match(
        rows in prop::collection::vec((any::<u64>(), any::<u8>()), 0..4096)
    ) {
        let old = select_active_before(&rows);
        let new = select_active_after(&rows);
        prop_assert_eq!(old, new);
    }
}
```

Инвариант **сравнивает последовательность полностью**, включая повторы, а не только множество ID. Если обе функции содержат одинаковую ошибку, сравнение её не выявит — нужны независимые требования/fixtures или отдельный oracle. Указанный пример следует запускать в crate с объявленной `proptest`; он не является частью `std`.

### 41.3. Miri для кода, использующего `unsafe` или сложное владение

```bash
rustup toolchain install nightly --component miri
cargo +nightly miri test
```

Запускайте на **совместимом host и наборе API**, желательно на ограниченном наборе чистых тестов. Miri — интерпретатор, он значительно медленнее нативного исполнения; нативные syscalls/FFI могут поддерживаться частично. Miri не заменяет обоснования aliasing, pinning, drop order, pointer provenance и lifetime. Официальный источник: [rust-lang/miri](https://github.com/rust-lang/miri/blob/master/README.md).

### 41.4. Fuzzing с неизменным эталоном

```bash
# В отдельном проекте, nightly и поддерживаемая платформа:
cargo install cargo-fuzz
cargo +nightly fuzz init
cargo +nightly fuzz add equivalent
cargo +nightly fuzz run equivalent
```

Пример содержимого `fuzz/fuzz_targets/equivalent.rs` после инициализации:

```rust
#![no_main]
use libfuzzer_sys::fuzz_target;
use rust_perf_case::{select_active_before, select_active_after};

fuzz_target!(|rows: Vec<(u64, u8)>| {
    assert_eq!(select_active_before(&rows), select_active_after(&rows));
});
```

Важны seed corpus из настоящих входов, timeout, ограничение размера/памяти и сохранение воспроизводимых падений. `cargo-fuzz` использует libFuzzer и требует инструментированного компилятора и поддерживаемой платформы; см. [официальный rust-fuzz/cargo-fuzz](https://github.com/rust-fuzz/cargo-fuzz). Для сетевого парсера проверяйте также аварийное завершение на повреждённых длинах, некорректных escape и UTF-8, а не только совпадение результатов двух версий.

### 41.5. Моделирование памяти: Loom

```rust
// [dev-dependencies] loom = "0.7"; отдельный тест/feature,
// не смешивать его примитивы с std::sync в моделируемом участке.
#[test]
fn publication_is_ordered() {
    loom::model(|| {
        use loom::sync::Arc;
        use loom::sync::atomic::{AtomicBool, AtomicUsize, Ordering};
        use loom::thread;

        let ready = Arc::new(AtomicBool::new(false));
        let payload = Arc::new(AtomicUsize::new(0));
        let r1 = Arc::clone(&ready);
        let p1 = Arc::clone(&payload);
        let writer = thread::spawn(move || {
            p1.store(7, Ordering::Relaxed);
            r1.store(true, Ordering::Release);
        });

        let r2 = Arc::clone(&ready);
        let p2 = Arc::clone(&payload);
        let reader = thread::spawn(move || {
            if r2.load(Ordering::Acquire) {
                assert_eq!(p2.load(Ordering::Relaxed), 7);
            }
        });
        writer.join().unwrap();
        reader.join().unwrap();
    });
}
```

`Release/Acquire` публикует данные только если чтение флага действительно наблюдает установленное значение. Простая замена на `Relaxed` в обоих обращениях к флагу **не сохраняет** этот протокол. Loom работает с собственными моделируемыми типами и стоимость перебора быстро растёт; [loom](https://github.com/tokio-rs/loom).

### 41.6. Sanitizers и ограничения

`AddressSanitizer` полезен для части ошибок нативной памяти, `ThreadSanitizer` — для некоторых data races; перед запуском уточните [поддержку инструментов в Rust Unstable Book](https://doc.rust-lang.org/nightly/unstable-book/compiler-flags/sanitizer.html). Часто нужны nightly, подходящий target и совместимая сборка `std`; не копируйте флаги произвольно в production. Sanitizers не являются доказательством отсутствия UB и не заменяют `cargo test`/Miri/Loom. Запуск sanitizer, fuzzing и Miri — **корректность**, а не benchmark; замеры скорости делаются отдельно в оптимизированной сборке без инструментирования.

## 42. Статистика производительности без выдуманного «+15%»

### 42.1. Что сохранять из эксперимента

Минимальный набор: `git commit` обоих вариантов, `rustc -Vv`, `cargo -V`, `RUSTFLAGS`, target triple, CPU model, ядра/частоты/governor, ОС, распределение входов, размер `n`, прогрев, порядок замеров, сырые времена **каждого независимого блока**, пиковая память, число аллокаций и критерий успешной оптимизации.

**Нельзя:** выбрать только лучший прогон, сравнить локальный `dev` с `release`, смешать разные бинарники в одном perf profile, замерять установку/генерацию входов у одного варианта и не замерять у другого, принимать <1% за доказанный прирост без достаточно строгого эксперимента.

### 42.2. Парные ABBA-блоки и разумный эффект

- Для одного фиксированного сценария выполните независимые прогретые блоки `A B B A`, затем `B A A B` (или сбалансированную случайную перестановку). Выносите генерацию входных данных из замера, если production-метрика не включает генерацию.
- В каждом блоке сохраняйте два значения `A` и два `B`, затем берите медиану каждого и отношение `A/B`. Если измеряете **время**, отношение >1 означает, что B быстрее.
- Анализируйте распределение отношений на независимых блоках, а не миллионы внутренних итераций как миллионы независимых экспериментов. Используйте bootstrap-интервал для медианы *логарифмов* парных отношений с фиксированным seed.
- Если 95% интервал включает 1.0 или предполагаемый выигрыш меньше заранее согласованного порога (скажем, 2% **как пример политики команды**, а не физический закон), вердикт `unknown`, а не `keep`. Для принятия решения учитывайте регрессии на других сценариях, RSS/p99 и сложность кода.
- При 20 вариантах и 20 сценариях растёт риск ложных находок. Устанавливайте число сравнений/семейство гипотез заранее, рассматривайте интервалы после коррекции за множественное тестирование или подтвердите выбранного победителя на **новой** независимой серии.

Пример формата CSV (числа здесь **искусственные и служат только примером синтаксиса**):

```csv
scenario,block,variant,ns
small,1,A,1200
small,1,B,1190
small,1,B,1210
small,1,A,1180
small,2,B,1205
small,2,A,1195
small,2,A,1215
small,2,B,1200
```

**Никакие числа в этом примере не являются измерением пользователя или исходного проекта.** Для реального CI сохраняйте CSV как артефакт и не стирайте outliers без предварительно сформулированного правила/технической причины.

### 42.3. Метрики CPU и их физический смысл

- `cycles` и `instructions` → отношение `IPC = instructions/cycles`, но значение само по себе не означает «лучше»; сравнивать **при одинаковой задаче** и похожих CPU-состояниях.
- `cache-misses` в общем `perf stat` не равно точному счёту L1D/LLC misses: названия и semantics PMU events зависят от CPU, target и доступности счётчиков.
- L1/L2/LLC/TLB, memory bandwidth, branch misses, frontend stalls, `perf c2c` и `perf mem` имеют смысл только для подходящей архитектуры и её perf events; спрашивайте, что именно указано в `perf list`.
- `perf record -g` — выборочное наблюдение (sampling); `perf annotate` помогает связать samples с инструкциями, но сложный pipeline и skid могут сместить адрес сэмпла.
- Для сервиса нужны ещё queue wait, число запросов, доля ошибок, p50/p95/p99 и нагрузка на момент измерения; p99 без размеров выборки и модели поступления запросов малоинформативен.

### 42.4. Выполняемый анализ ABBA-CSV без сторонних Python-пакетов

В приложенном архиве `rust_perf_case/scripts/analyze_abba.py` реализована парная оценка `median(A/B)` и percentile-bootstrap 95% интервала по **независимым блокам**. Это не симуляция результата Rust и не замена контролируемого эксперимента.

```bash
# Подставьте СВОЙ CSV с реальными измерениями:
python3 rust_perf_case/scripts/analyze_abba.py results.csv

# Искусственный пример только для проверки формата, НЕ для отчёта об ускорении:
python3 rust_perf_case/scripts/analyze_abba.py rust_perf_case/scripts/sample_synthetic.csv
```

Без минимум 10 независимых парных блоков скрипт отмечает вывод как разведочный; при интервале, содержащем 1.0, вердикт `uncertain`. Даже при узком интервале нужны проверка репрезентативности, отсутствие систематического дрейфа, независимая репликация и оценка нескольких сценариев. Bootstrap-оценка может ошибаться при зависимых блоках и систематическом смещении.

### 42.5. Заключение отчёта в одном строгом формате

```text
HYPOTHESIS:       уменьшить realloc в dense-filter, не менять порядок ID
BASELINE (A):     commit <sha>; flags; compiler; platform
CANDIDATE (B):    commit <sha>; одинаковые flags/compiler
WORKLOAD:         n=[64,4096,262144], active=[1%,50%,99%]
CORRECTNESS:      cargo test: [действительный результат/не запускалось]
MEASUREMENT:      CSV raw data; независимые блоки; образцы/частоты
EFFECT:           median(A/B) + 95% CI, только из реальных данных
COUNTER-METRICS:  RSS, allocations, p99, compile time
DECISION:         keep/revert/unknown, с отдельной причиной для каждого сценария
```

При недоступности rustc/perf вводите **`not executed`**, а не выдуманный показатель. Помните: критерии существуют, чтобы исключать ложные успехи, а не «гарантировать 90%» или «ускорять всё».

## 43. Воспроизводимый кейс: `Vec::with_capacity` при фильтрации

В состав архива этой редакции включён отдельный Cargo-проект **`rust_perf_case/`** со структурой:

```text
rust_perf_case/
├── Cargo.toml
├── src/lib.rs
├── tests/select_active.rs
├── benches/select_active.rs
├── scripts/smoke.sh
└── README.md
```

**Гипотеза:** если почти каждый входной объект попадает в результат, `Vec::with_capacity(rows.len())` потенциально уменьшит `realloc`. Если выбирается только 1% объектов, резервирование под все 100% может создать большой избыточный буфер и ухудшить память/скорость. На маленьких `n` стоимость лишнего резервирования также может перевесить.

### 43.1. Две кандидата — одинаковый результат

```rust
pub fn select_active_before(rows: &[(u64, u8)]) -> Vec<u64> {
    let mut output = Vec::new();
    for &(id, active) in rows {
        if active != 0 { output.push(id); }
    }
    output
}

pub fn select_active_after(rows: &[(u64, u8)]) -> Vec<u64> {
    let mut output = Vec::with_capacity(rows.len());
    for &(id, active) in rows {
        if active != 0 { output.push(id); }
    }
    output
}
```

Семантика: обрабатываем все входы, ненулевой `active` = true, порядок и повторы ID сохраняются. Эквивалентность **не означает** одинаковый `Vec::capacity()` — публичное значение capacity может быть наблюдаемым, если программа полагается на него. При выходе за ресурсные лимиты обе реализации также могут разным образом завершить выделение памяти. Если capacity/обработка allocation failures входят во внешний контракт — это не drop-in правка.

### 43.2. Матрица тестов и измерений

| Размер входа | Доли выбранных строк | Что именно изучаем |
|---|---|---|
| 0, 1, 2, 3, 31, 32, 33 | 0%, 1%, 50%, 100% | краевые случаи и tiny-n overhead |
| 64, 4 096 | 1%, 50%, 99% | overhead, неизвестный заранее threshold |
| 262 144 | 1%, 50%, 99% | стоимость аллокаций, RAM/cache и throughput |

Приложенный benchmark использует [Criterion 0.8.2](https://docs.rs/crate/criterion/0.8.2), данные формируются **вне** замеряемого участка, а `black_box` стоит на границе функции, не на каждом элементе. В нём **нет фиктивных результатов**: он выдаст числа только после запуска на вашей машине.

### 43.3. Команды воспроизведения

```bash
cd rust_perf_case
rustc -Vv
cargo -V
cargo generate-lockfile            # один раз, затем сохраните Cargo.lock
cargo fmt --all -- --check
cargo test --locked --all-targets
cargo clippy --locked --all-targets -- -D warnings
cargo bench --locked --bench select_active
```

Для воспроизводимости храните `Cargo.lock` вместе с полученным raw report. Версия Criterion закреплена в `Cargo.toml`, но без `Cargo.lock` транзитивные зависимости ещё могут меняться; `generate-lockfile` требует доступного registry. Доступность некоторых зависимостей зависит от хост-платформы, а результаты бенчмарка — от CPU. Команда `cargo test --all-targets` может собирать bench target; основное измерение делайте командой `cargo bench`.

**Как решать:** выигрыш только в плотном сценарии при ухудшении RSS в разреженном — не универсальная оптимизация. Рассмотрите `reserve` с более точной оценкой selectivity или повторное использование буфера, **если** это согласуется с контрактом. Бенчмарк специально устроен так, чтобы возможна была и регрессия: это более честная проверка, чем заранее выбранный «красивый» пример ускорения.

## 44. Async/Tokio и p99: куда уходит задержка за пределами функции

### 44.1. Разделите задержку на участки

Для энд-ту-энд запроса концептуально:

\[
L_{end-to-end}=L_{admission}+L_{queue}+L_{schedule}+L_{work}+L_{I/O}+L_{response}
\]

Это **модель разложения** для инструментирования: фактические операции могут перекрываться во времени, и сумма эксклюзивных отрезков требует аккуратного выбора границ. Время исполнения обработчика `work` не равно пользовательской p99. Если CPU почти не занят, возможна очередь, сетевое ожидание, блокировка mutex или недопущенная нагрузка в генераторе запросов.

### 44.2. Инструменты, которые дополняют обычный CPU-flamegraph

| Инструмент | Что даёт | Типичный риск |
|---|---|---|
| [`tracing`](https://docs.rs/tracing/latest/tracing/) | Структурированные spans, request/task IDs | Слишком частые события влияют на overhead и аллокации |
| [`tokio-console`](https://github.com/tokio-rs/console) | Мониторинг async task, busy/idle/scheduled | Требует инструментирования и совместимого runtime; не измеряет весь end-to-end путь |
| [`tokio-metrics`](https://docs.rs/tokio-metrics/latest/tokio_metrics/) | Метрики задач/планировщика | Зависит от версии runtime/feature и структуры нагрузки |
| `perf` + off-CPU профилировщик | CPU samples и ожидания/блокировки | Разные источники времени и системная поддержка |
| Open-loop нагрузочный генератор | Заданная **скорость поступления** запросов, даже если сервис тормозит | Нужен генератор, способный поддерживать заданную интенсивность |
| `hdrhistogram` / latency recorder | Структура хвостов, throughput/p99 | Слишком мало запросов для стабильного p99; нельзя игнорировать пропущенные запросы |

**Coordinated omission:** если генератор ждёт завершения ответа прежде чем отправить следующий запрос, он автоматически снижает нагрузку на медленной системе и может недооценивать хвостовую задержку. Для оценок latency под заданным потоком запросов фиксируйте planned arrival time, а не только старт фактически допущенного запроса. Два генератора с одинаковым «1000 requests» могут давать несопоставимые p99.

### 44.3. Упрощённый пример: blocking работа вне async worker

```rust
// Требуется Tokio 1.x и runtime с rt-multi-thread.
async fn checksum_heavy(data: Vec<u8>) -> Result<u64, tokio::task::JoinError> {
    tokio::task::spawn_blocking(move || {
        data.iter()
            .fold(0_u64, |sum, &x| sum.wrapping_add(u64::from(x)))
    }).await
}
```

`spawn_blocking` не делает CPU-bound работу быстрее сам по себе и может создать слишком много конкурирующих задач; нужен контроль concurrency (например, semaphore), а для устойчиво CPU-bound пула стоит измерить отдельный Rayon-пул. Успешный `JoinHandle` здесь обёрнут в `Result`; паника/отмена не игнорируются. В реальном приложении требования к отмене, shutdown и памяти нужно формализовать отдельно.

### 44.4. Чек-лист высоконагруженного сервиса

- Нагружайте 1, 2, 4, ... конкурентных клиентов при фиксированном rate **и** в режиме насыщения, измеряйте throughput и p99 одновременно.
- Собирайте span времени ожидания очереди отдельно от времени `poll`/CPU; большие p99 часто не исправляются SIMD над микрофункцией.
- Измеряйте размер очереди, число отклонённых сообщений, backpressure, таймауты и распределение размеров payload; очереди без ограничения способны неограниченно удерживать память.
- Сравнивайте разные сценарии: steady-state, burst, деградация сети, отказ dependency, исчерпание пула, обработка отмены.
- Не пишите sync `std::fs`, `std::thread::sleep` или тяжёлую CPU-задачу прямо внутри короткого async event handler; при необходимости разбивайте или выносите с обоснованным контролем concurrency.

## 45. Build/CI: воспроизводимость, профили и минимальная версия Rust

### 45.1. Три разные задачи: build-time, runtime, distribution

| Цель | Первые команды | Что не путать |
|---|---|---|
| Ускорить компиляцию | `cargo build --timings`, `cargo check`, `cargo tree -e features` | Быстрая сборка не равна быстрому бинарнику |
| Ускорить приложение | `cargo build --release`, `perf`, Criterion/hyperfine | `opt-level=3` уже default в release |
| Уменьшить файл | `cargo bloat`, `size`, `strip`, `opt-level=z/s` | Размер бинарника != RSS/рабочий набор |
| Проверить переносимость | `cargo +<msrv> test`, `rustc --print target-list` | `target-cpu=native` зависит от CPU сборщика |
| Повторить эксперимент | lockfile, хеш коммита, raw sample/flags | `cargo update` и смена toolchain могут изменить результат |

`cargo build --timings` — **стабильный** режим; HTML-отчёт появляется в `target/cargo-timings/`. Из него видно параллельные/долгие единицы компиляции; макросы, build scripts, generic-мономорфизация и тяжёлые crate могут быть важнее флагов линковки. [Cargo timings](https://doc.rust-lang.org/cargo/reference/timings.html).

### 45.2. Как проверять MSRV без скрытого повышения требований

```toml
# Cargo.toml (пример для проекта с минимальным Rust 1.88)
[package]
name = "example"
version = "0.1.0"
edition = "2021"
rust-version = "1.88"
```

```bash
rustup toolchain install 1.88.0 1.99.1
cargo +1.88.0 test --all-targets
cargo +1.99.1 test --all-targets
cargo +1.99.1 build --release
cargo +1.99.1 build --timings
cargo +1.99.1 tree -e features
```

Это **пример**, не готовый `Cargo.toml` настоящего проекта. Если в коде использованы `Vec::push_mut` или `format_into`, минимальный компилятор должен быть увеличен до 1.95+ или 1.98+ соответственно; при наличии сторонних crates учитывайте также их MSRV. Команды требуют установленных target и зависимостей. Устанавливать MSRV равным последнему stable без необходимости — не всегда хороший выбор для библиотек.

### 45.3. Учёт изменений Cargo 1.99/1.100

Cargo 1.99 ввёл встроенный профиль `debug` как подготовку к возможному изменению поведения `dev`. Он также изменил поведение incremental в среде с переменной `CI`. В **beta 1.100** меняется внутренний layout build artifacts; внутренняя структура `target/` не является частью стабильного интерфейса Cargo. Не прописывайте глобальный `RUSTFLAGS=-Ctarget-cpu=native` в кроссплатформенную CI-матрицу.

```bash
# Получить фактические пути артефактов через машинные сообщения Cargo:
cargo build --release --message-format=json > cargo-build.jsonl
# Каждая строка — JSON; обрабатывайте compiler-artifact.filenames, не regex по target/.
```

Этот JSON log предназначен для машинной обработки; сообщения содержат разные `reason`, поэтому фильтруйте только `compiler-artifact`, а не берите последнюю JSON-строку. [Cargo external tools](https://doc.rust-lang.org/cargo/reference/external-tools.html), [Cargo beta changelog](https://doc.rust-lang.org/beta/cargo/CHANGELOG.html).

### 45.4. Инструкция по релизному CI

Критические проверки — **на stable и заявленном MSRV**, дополнительная матрица на beta для предупреждения о будущих регрессиях. Ошибки beta до выхода не обязаны блокировать production, но должны попадать в задачу. Отдельная nightly job — Miri, если для проекта это применимо. Benchmarks CI нужны на предсказуемом dedicated runner; общие облачные runners часто слишком шумные для решений о приросте 1–2%.

**Пример политики релизного review:** PR не получает метку `performance win`, пока не приложены семантические тесты, реальные результаты с raw samples, конфигурация машины, минимум 2 разных масштаба входа и описание tradeoffs. Досрочная оптимизация разрешена только для очевидных устранений лишней работы, но тогда это *кандидат*, а не опубликованная численная победа.

## 46. Редакционный аудит, первоисточники и обновление гайда

### 46.1. Исправления относительно исходной редакции

| Что было | Что изменено | Почему |
|---|---|---|
| `Vec<bool>` описывался как битово упакованный контейнер | Исправлено на `bool` = 1 байт, `Vec<bool>` не bitset | Фактическая ошибка могла привести к неправильной оптимизации памяти |

| Не было воспроизводимого Cargo-кейса | Добавлен `rust_perf_case/` с Criterion и тестами | Можно проверить гипотезу самостоятельно без выдуманного x% |

### 46.3. Чек-лист сопровождения, чтобы не переписывать весь файл каждые 6 недель

1. Указать дату проверки, последнюю **patch** stable-версию и rustc `-Vv`. Если опубликована новая stable, устаревшие значения переписать, не оставлять статуса «сейчас» без даты.
2. Сверить релиз с [официальным changelog](https://doc.rust-lang.org/releases.html); новые API занести в матрицу `name → stable version → пример → риск → тест`. Без подтверждения не переводить в stable.
3. Для каждого beta-кандидата повторно проверить сигнатуру `cargo +beta check` и официальную публикацию; отложенные/отменённые стабилизации вернуть в watchlist. **Не назначать даты** PR без подтверждения Rust Team.
4. Запустить `cargo +<MSRV> test`, `cargo +stable test`, `cargo +beta test`, Miri/fuzz/CI по применимости; все результаты записать как *успешно / ошибка / не выполнялось*.
5. Сравнить compiled snippets и обнаружить устаревшие `RUSTFLAGS`, оптимизационные допущения, deprecated APIs и behaviour changes. Не утверждать ускорение без raw measurements.
6. Пересмотреть номер, статус, известные регрессии Cargo/LLVM/targets и упоминания beta/nightly; обновить ссылки. Сохранить changelog и известные незакрытые TODO.

### 46.4. Что подтверждено, а что остаётся непроверенным

**Подтверждено источниками и статической редакторской проверкой (2026-11-09):** актуальность официального stable-релиза 1.99.1, расписание 1.100 beta / 1.101 nightly, API из опубликованных релизов 1.95–1.99, наличие черновика 1.100 с аллокаторами и sample PGO, существование Criterion 0.8.2, факт что `Vec<bool>` не bit-packed, документация `as_chunks` 1.88+, доступность перечисленных средств тестирования.

**Не выполнено в среде редактирования:** компиляция всего исходного каталога примеров и нового Cargo-проекта, `cargo test`, `cargo bench`, `cargo miri test`, запуск профилировщика на вашем CPU, измерение производительности. В этой среде **нет `rustc`/`cargo`**; поэтому никакие проценты ускорения в этом документе не заявлены и ни одному новому примеру не присваивается отметка «скомпилировано», пока пользователь не выполнит команды в своей среде. Некоторые старые фрагменты исходного гайда специально служат иллюстрациями с осознанно изменёнными контрактами.

Сохранённые рассуждения исходного справочника о двух сторонних видео рассматриваются как **материал предыдущей редакции**, а не независимое подтверждение их benchmark-чисел. Сырых видеоматериалов для повторной проверки в этом выпуске нет.

### 46.5. Финальный практический принцип

**Оптимизация считается подтверждённой только при одновременном выполнении трёх условий:** контракт сохранён (или изменение явно разрешено), профиль и измерения подтверждают улучшение на нужной нагрузке, а стоимость регрессий/поддержки оправдана. Если доказательств недостаточно — это проверяемая гипотеза, а не факт.
