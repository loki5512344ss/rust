### 47.2. Один последовательный workflow: `hyperfine` → `samply`/flamegraph → DHAT → правка → повторный профиль

Эпизоды из `videoplayback.1mp4` и `videoplayback2.mp4` показывают важную инженерную связку, которая была раздроблена по ранним разделам. Ниже — **воспроизводимый сценарий**, а не запись реальных результатов из видео.

1. **Честно фиксируйте end-to-end время** на неизменном входе, отделяя запуск процесса от прогрева и от собственно работы алгоритма:

```bash
cargo build --release
hyperfine --warmup 3 --runs 15 './target/release/my_program input.txt'
```

2. **Собирайте CPU-профиль** того же сценария, а не другого искусственного теста:

```bash
# Установите samply отдельно: cargo install --locked samply
# Команда пригодна, если инструмент поддерживает ОС и доступны разрешения профилировщика:
samply record ./target/release/my_program input.txt
```

`samply` открывает профиль в интерфейсе Firefox Profiler; **это не значит, что программа должна исполняться в браузере**. На Linux применяются аппаратные/perf-события и могут понадобиться права; профиль, записанный на macOS, не равен Linux/x86-64 профилю. `samply` присутствует в §4, но там не был показан полноценный цикл. Источник: [samply README](https://github.com/mstange/samply/blob/main/README.md).

3. **Если время уходит в аллокации**, проверьте частоту и место выделений через DHAT в отдельной диагностической сборке, а не только суммарный RSS:

```toml
# Дополнение в Cargo.toml проекта, если зависимость ещё не установлена:
[features]
dhat-heap = []

[dependencies]
dhat = "0.3" # Проверить актуальную совместимую версию перед фиксацией lockfile
```

```rust
// В crate root. Запускайте только в инструментированной сборке.
#[cfg(feature = "dhat-heap")]
#[global_allocator]
static ALLOC: dhat::Alloc = dhat::Alloc;

fn main() {
    #[cfg(feature = "dhat-heap")]
    let _profiler = dhat::Profiler::new_heap();

    // Здесь выполняйте ТОТ ЖЕ реальный сценарий, который анализируете.
    // Не вызывайте std::process::exit, иначе деструктор профайлера не выполнится.
}
```

Запуск: `cargo run --release --features dhat-heap -- input.txt` (аргументы нужно обработать в вашей программе). Фича изменяет аллокатор и накладные расходы, поэтому **DHAT нельзя использовать как обычный speed benchmark**. Сохраните `dhat-heap.json` и сравните по месту создания, числу и срокам жизни аллокаций. Источник: [dhat crate docs](https://docs.rs/dhat/latest/dhat/).

4. **Сформулируйте проверяемую гипотезу** по профилю: например, лишнее клонирование слова при каждом повторном появлении в файле, repeated parse, неверный выбор `HashMap` либо двойной lookup. Одно изменение — один diff.

5. **Отдельно подтвердите эквивалентность и выигрыш:** property-tests/fixtures на пустых файлах, не-UTF-8, ошибках ввода, повторяющихся ключах и переполнении счётчика; затем повторите шаг 1, а **только при устойчивом эффекте** повторите шаг 2. Если профиль сдвинулся на другое узкое место, это ожидаемый результат, но не доказательство уменьшения end-to-end времени.

| Тип профиля | Доказывает | НЕ доказывает |
|---|---|---|
| `hyperfine` | Распределение end-to-end времени конкретной команды | Какая функция замедляет её |
| `samply`/flamegraph | В каких стэках CPU тратит семплируемое время | Количество аллокаций, блокировки, wall-time каждого вызова |
| DHAT | Паттерны выделений/жизни объектов в инструментированной версии | Runtime-ускорение, эквивалентность поведения |
| `perf stat`/Top-Down | Общие аппаратные симптомы на поддерживаемом CPU | Автоматическое указание на единственный виновный Rust-метод |

### 47.3. Ускорение компиляции: debug-info, parallel frontend и Cranelift

В `videoplayback3.mp4` демонстрируются **три разных механизма**. Их нужно измерять **раздельно**, потому что они влияют на разные стадии компиляции и имеют разную доступность.

**A. Stable: уменьшить объём debug-информации в `dev`.** Это не ускоряет релизный runtime и не должно подменять полноценный дебаг с inspect переменных:

```toml
# Cargo.toml
[profile.dev]
debug = "line-tables-only"

[profile.dev.package."*"]
debug = false

[profile.debugging]
inherits = "dev"
debug = true
```

Обычный `cargo build` собирает облегчённый dev; `cargo build --profile debugging` — вариант с полной debug-информацией для workspace-crate. При необходимости полной информации и в зависимостях добавьте в этот custom profile явное переопределение `package."*".debug = true` и проверьте итоговую настройку, поскольку настройки для зависимостей могут наследоваться. Официальная рекомендация: [Cargo — Optimizing Build Performance](https://doc.rust-lang.org/cargo/guide/build-performance.html). Ограничение: легче debug info = хуже возможности инспекции локальных переменных.

**B. Nightly-only: параллельный frontend `rustc`.** На кадрах показан `-Zthreads=8`:

```bash
# Временный эксперимент; не добавляйте -Z в стабильную конфигурацию:
RUSTFLAGS='-Zthreads=8' cargo +nightly check
```

Это не то же самое, что Cargo `-j 8`: `-j` ограничивает параллельные независимые задания, а `-Zthreads=N` влияет на параллельную работу **внутри rustc**, где она поддерживается. Избыточное количество потоков на общей машине может ухудшить производительность. Nightly-флаг и его доступность меняются; проверяйте по [Cargo Book](https://doc.rust-lang.org/cargo/guide/build-performance.html) и `rustc +nightly -Z help`.

**C. Nightly-only: альтернативный backend Cranelift.** По состоянию на редакцию гайда соответствующий Cargo-механизм нестабилен и требует nightly:

```bash
rustup component add rustc-codegen-cranelift-preview --toolchain nightly
CARGO_PROFILE_DEV_CODEGEN_BACKEND=cranelift cargo +nightly build -Zcodegen-backend
```

Используйте для *быстрого edit-build-run*, **не для продакшен-бенчмарков**, так как скорость сгенерированного кода и поддержка части возможностей могут отличаться от LLVM. Доступные targets и возможности проверяются по [официальному README Cranelift](https://github.com/rust-lang/rust/blob/main/compiler/rustc_codegen_cranelift/Readme.md) и [Cargo Book](https://doc.rust-lang.org/cargo/guide/build-performance.html). Никакие «−46% build-time» со слайда не переносим без пересборки и замеров на вашей машине.

**Протокол сравнения:**

```bash
rustc -Vv
cargo -V
cargo build --timings
# Изучите target/cargo-timings/cargo-timing.html
```

Измеряйте *два* сценария: clean build в новых одинаковых build directories и incremental rebuild после одинаковой правки. Используйте отдельные `CARGO_TARGET_DIR` для stable и экспериментальных конфигураций; сравнивайте несколько повторений при стабильной загрузке CPU/диска и записывайте размер артефактов. `cargo build --timings` показывает путь по критической зависимости и время каждого compilation unit, **не ускоряет сборку самостоятельно**. Источник: [Cargo — Build Timings](https://doc.rust-lang.org/cargo/reference/timings.html).

### 47.4. Практический pipeline: подсчёт top-users и опасные «быстрые» замены

В `videoplayback6.mp4` (~01:00–05:00) виден сценарий `top_users(log)` с наивной схемой `contains_key` → `insert` → `get_mut`, затем сортировка всех счётчиков и `truncate(10)`. Это полезный **сквозной кейс**, объединяющий техники, уже описанные отдельно в §§5, 7, 19, 26.

Предлагаемый **иллюстративный вариант**, не переписанный из кадра дословно:

```rust
use std::collections::HashMap;

fn top_users(log: &str, limit: usize) -> Vec<(String, u64)> {
    let mut counts: HashMap<&str, u64> = HashMap::new();
    for line in log.lines() {
        // В этом образце контракт: неверно сформированная строка пропускается.
        // Если исходный контракт был panic/error — так менять нельзя!
        if let Some(user) = line.split(',').nth(1) {
            *counts.entry(user).or_insert(0) += 1;
        }
    }

    let mut ranked: Vec<(&str, u64)> = counts.into_iter().collect();
    // Для равных счётчиков договоримся о стабильном лексикографическом tie-break.
    ranked.sort_by(|(a, ac), (b, bc)| bc.cmp(ac).then_with(|| a.cmp(b)));
    ranked.truncate(limit);
    ranked.into_iter().map(|(user, n)| (user.to_owned(), n)).collect()
}
```

**Какие контракты надо проверить ДО замены:**

- Исходная программа могла `unwrap()` при некорректном логе; новый `if let` пропускает строку, значит **меняет поведение**. При требовании строго одинакового результата сохранить правило обработки ошибок.
- `u64 += 1` переполняется согласно профилю/overflow-checks; если счётчики могут достичь предела, заранее зафиксировать правило `checked_add`, `saturating_add` либо `wrapping_add` **для обеих реализаций**.
- Обычный `HashMap` не задаёт порядок обхода; явный tie-break меняет произвольный прежний порядок при равных счётчиках, хотя делает API предсказуемее. При строгой эквивалентности нужно сохранить старый контракт, а не «улучшать» его неявно.
- При `limit ≪ distinct_users` сортировка *всех* ключей остается лишней; можно проверить ограниченную min-heap или `select_nth_unstable_by`. Но при стабильности равных ключей нужна полная спецификация сравнителя. Нет бесплатного улучшения для любого распределения.
- `HashMap<&str, u64>` ссылается на исходный `log`; безопасно лишь пока входной буфер жив. Клонируются **только итоговые** имена. Это не эквивалент API, который должен сохранять произвольные ссылки на сырые строки логов.

Другой эпизод ролика (~05:30–06:45): замена `sessions.remove(idx)` на `sessions.swap_remove(idx)`. Показанные микросекунды/наносекунды зависят от размера `Vec` и индекса; `swap_remove` выполняет O(1) перемещение последнего элемента, **но нарушает порядок и может сломать индексы сессий**, сохранённые в других структурах. Источник: [std::Vec::swap_remove](https://doc.rust-lang.org/std/vec/struct.Vec.html#method.swap_remove). При порядковой семантике оптимизация недопустима — независимо от эффектного процента ускорения в видео.

**Тестовые наборы:** пустой лог, malformed CSV, одинаковое число запросов у нескольких пользователей, отсутствие пользователей, `limit=0`, `limit>unique`, большие сообщения, повторяющиеся строки и случаи с миллионами ключей. Сравните выходы и allocations/op, `ns/op` для разных распределений, не только один удачный бенчмарк.

### 47.5. Советы Rust-разработчика из «21+ Pro Tips»: что связано с производительностью косвенно

В `videoplayback7.mp4` показаны `dbg!`, `rust-toolchain.toml`, статическая/динамическая диспетчеризация, типобезопасные парсеры, typestate, `cargo deny` и инструменты CI. **Большинство — инструменты качества, не оптимизации скорости.** Нельзя приписывать ускорение `dbg!`, typestate или `cargo deny` без измеряемого механизма.

Что действительно полезно для воспроизводимости экспериментов:

```toml
# rust-toolchain.toml в репозитории: зафиксируйте ПОНИМАЕМЫЙ канал/версию.
[toolchain]
channel = "1.99.1"
components = ["clippy", "rustfmt"]
profile = "minimal"
```

```bash
rustup show active-toolchain
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
# Если установлены внешние инструменты:
cargo nextest run --locked   # тестовый раннер, не benchmark
cargo deny check             # политика зависимостей, не ускорение runtime
```

`rust-toolchain.toml` помогает связать измерения с конкретным компилятором, но версия `1.99.1` здесь **снимок на дату документа**, а не вечная рекомендация и не MSRV. Для быстрых итераций профилирование времени сборки ведите отдельно от скорости тестируемого кода; для статической диспетчеризации сравнивайте runtime **и** binary-size/compile-time.

### 47.6. Что не переносить из видео как «факты об ускорении»

1. **Разовые проценты и «×7000».** На слайдах отсутствует воспроизводимый набор входов и независимый повтор на целевом железе; их можно цитировать только как *числа из чужой демонстрации* с полным контекстом, а не как гарантию.
2. **`-Zthreads` и Cranelift не относятся к stable 1.99.1.** Их включение в production-`.cargo/config.toml` без условия сломает стабильную сборку.
3. **`swap_remove`, `sort_unstable`, замена `String` на массив и смена `panic` на `skip`** могут изменять контракт. При несовпадении результатов ускорение нельзя засчитывать.
4. **`dbg!` и `println!` не должны оставаться на горячем пути** при сравнении; `dbg!` всегда вычисляет переданный аргумент и может заметно исказить измерение.
5. **Статическая диспетчеризация не означает «всегда быстрее».** Generic-мономорфизация может увеличить время сборки и машинный код, а indirect branch иногда дешевле перегруженного I-cache. См. §14.
6. **Советы по собеседованиям и архитектурные mockups** из последнего ролика не являются исследованием производительности Rust; они не добавлены к каталогу runtime-трюков.

### 47.7. Мини-матрица проверки новых разделов

| Проверка | Статус при редактировании | Что требуется для подтверждения |
|---|---|---|
| Девять входных видео | Да: медиафайлы открыты, просмотрены кадры и кодовые сцены по всей длительности | Полная аудиорасшифровка для утверждений о репликах авторов; здесь таких утверждений нет |
| Команды `samply`, `cargo --timings`, debug-info и Cranelift | Текст и режимы проверены по официальным документам | Запуск на подходящем Linux/macOS/Windows target |
| `top_users` и демонстрация удаления | Пример синтезирован по видимой задаче; Rust-компилятор в среде редактирования отсутствует | `cargo fmt`, `cargo test`, property/differential и Criterion на выбранном MSRV |
